## 1. Problem: the directive and the gap this doc closes

The owner's binding directive on #820 is **"completely and securely."** The orchestrator's plan comment (Phase 2, this lane) translates that into a definition of complete:

> the design must answer the credential plane **as a whole**, not just the provider-key file — explicit disposition of all three siblings (#820 raw keys at rest, #823 agent-readable control token on :4096, #825 enforcement) with either a fix or a documented residual-and-rationale; threat model must include prompt-injected exfiltration over the existing egress paths (gh, API, git) not just file reads; and the #1500 adversarial proof bar applies (probes that PROVE the agent cannot recover the key through every documented surface, including indirect ones).

Design 0058 is the provider-key half and is adopted as-is (Part A). What no existing document does is stand over the **entire plane**: every credential that exists in uid-1000-reachable space, every channel it could leave through, and a proof that the dispositions hold. That whole is this doc's scope.

## 3. What "the untrusted agent" means here (the trust line, one paragraph)

The agent process — opencode plus every tool subprocess it spawns — runs as uid 1000 and executes arbitrary user-repo code. Anything uid 1000 can read is one prompt-injection away from exfiltration over any reachable egress. Unix permissions cannot draw a line *inside* uid 1000 (the 2026-08-14 verification's rejected option 3; re-affirmed by the tiers WIP's own framing: the deny tier is real enforcement for *tool-mediated* reads, while arbitrary code reads directly). Therefore the only structural fixes are **removal from uid-1000 space** (C1) and **surface minimization with declared, measured residuals** (C2/C3 — file and env residuals survive by design where a consumer requires them; the sweep asserts their presence as expected); everything else is bounding the *sink* (#821) or accepting principal-owned presence (C4). Design 0051's uid-2000 sidecar is the boundary the platform already has; where a fix below needs a second uid, it uses that one, not a new one.

### Part B — The control token (#823): surface removal + the honest session residual

**B1. The credential wires (r4 — topology corrected; the r1-r3 sidecar premise was backwards).** The workspace password reaches uid-1000 space through THREE distinct wires, not two, and none of them is a sidecar-only path:

- **(w1) the file** — `init_fs` installs `/sandbox-cfg/password` 0600 from the projected Secret in BOTH modes (`init_fs.go:205`; the init container runs before the main container either way).
- **(w2) the supervisor's container env** — the controller wires `OPENCODE_SERVER_PASSWORD` as a secretKeyRef **on the uid-1000 workspace container** (`agentd_sidecar.go:342` — appended to `main := pod.Spec.Containers[0]`, the supervisor+opencode container; the r1-r3 text misattributed this to the uid-2000 sidecar, whose same-Secret copy is the differently-named `AGENTD_SIDECAR_PASSWORD` at `:105`). **This wire is STRUCTURAL in sidecar mode:** the supervisor presents it as the PULL Basic credential (`supervisorSpawnCredential()` = `os.Getenv`, `spawn_env_pull.go:151-153`; the security-shape comment at `:22-26` documents this as the design-0051 D1 carve-out — the alternatives, `agentdPassword` and the admin bearer, are D1-forbidden in uid-1000 space). Removing it requires a PULL-auth redesign (a projected per-pod pull token, distinct from the opencode control token) — a seam this doc names but does not design.
- **(w3) the opencode child's env** — inherited from the supervisor's environ at exec (`buildEnvFrom` → `os.Environ()` → `scrubAdminEnv` → child env, `secrets.go:1314-1370`, `managed_process.go:544`); the spawn-env PULL payload NEVER carries it (the served delta is exactly the materialized secrets-env content, `spawn_env_pull.go:173-183`).

Disposition:

- **(w1) the file:** audit sidecar-mode consumers — every agentd-side consumer holds the env form, so the file is likely vestigial there and removable; single-container keeps it as the one at-rest surface. Structural closure of the file surface remains "sidecar mode + consumer audit."
- **(w2) supervisor env: DECLARED STRUCTURAL RESIDUAL in SIDECAR mode only** (PULL auth; D1 forbids the alternatives — the seam for closure is a projected per-pod pull token, named not designed). **Single-container mode has NO w2 wire (r5 correction):** the controller wires no container-env form there; the supervisor reads the file at boot (`main.go:161-162`) and holds the credential in heap (`bootAgentPassword`) — a process-memory surface declared under the memory rows, not an environ surface.
- **(w3) child env: removable pending A3** — FD-at-exec (B2). Until the upstream FD-read lands, this surface is structural-inherited; the sweep declares it per-phase.

**B2. Child-env surface — FD-at-exec (r4: same-container, no boundary to cross).** In BOTH modes the supervisor execs opencode **in its own container** (sidecar mode: the workspace container runs agentd `supervise-opencode`, `agentd_sidecar.go:324-325`, which execs opencode via `opencodeServeCmd`, `managed_process.go:529-546`; the sidecar spawns no children — `agentd_sidecar.go:25-27`). FD inheritance at exec is therefore trivially available spawner-side — no cross-container passing exists or is needed (the r2/r3 "sidecar exec" premise and its fallback machinery solved a nonexistent topology): the supervisor writes the password to a pipe, passes the read end as fd 3 on the opencode exec, scrubs `OPENCODE_SERVER_PASSWORD` from the child's env slice, opencode reads it to memory at boot and closes the FD. `/proc/<opencode>/environ` no longer carries it; the FD exists for milliseconds at boot. **Gated solely on A3** (opencode-side FD-read — upstream batch item 2). The r2 pipe-then-file fallback is WITHDRAWN: it existed for the nonexistent cross-container case; if A3 never lands, w3 is simply a declared structural residual like w2 — there is no in-repo workaround, and pretending otherwise was the r3 failure.

**B2b. Disposition of #823's fix options, by name.** Option 1 (token unreadable by agent — root-owned file/env-free delivery) is B1/B2 above, with the single-container residual stated. Option 2 (short-lived per-session tokens rotated on operator connect) is **rejected via §9's two-token row** (the authorization layer does not exist upstream; same class as the in-pod RBAC rejection). Option 3 (audit-log operator-vs-agent origin on `:4096` connections) is **deferred to the B3 seam**: opencode does not expose connection-origin attribution, and agentd cannot observe direct in-pod `:4096` connections it does not proxy — origin-audit becomes native when operator traffic terminates at agentd (0055's end state). Near-term detection of `:4096` abuse rides the tiers' ask-tripwire on tool-mediated credential reads (the acquisition path), not the connection itself.

**B3. The residual, stated honestly: operator-session takeover.** C2's *impact* (not just its secrecy) is what #823 filed: a holder of the token can drive `:4096` as the operator — continue their conversation, impersonate them to the model. B1 removes the file surface (where consumerless) and B2 removes the child-env surface **when A3 lands**; w2 remains the declared structural residual — but opencode (uid 1000) must hold the verifier in memory regardless. **Mechanism restated (r2):** the acquisition path is same-uid process-memory access — procfs-adjacent reads where the runtime permits them, harness-mediated reads, or the upstream sandbox's escape class — NOT bare ptrace, which the deployed runtime (cap-drop-ALL, NoNewPrivs, gVisor opt-in) largely denies (A8). The residual survives on 0051's trust line — same-uid compromise is pod compromise by design — whatever the exact read mechanism; the sweep's memory row measures acquisition *difficulty*, and A8's spike decides how that row is probed. Within the current trust model that is the same line design 0051 §3 draws (same-uid compromise = pod compromise). The **structural** closure of operator-impersonation is authorization, not authentication: opencode has no session-scoped ACL ("this connection may only continue session X"), so *any* in-pod holder of *any* valid token is operator-equivalent. Disposition: **documented residual + named seam.** The seam is design 0055's end state — when the operator's interactive traffic terminates at agentd's session-state authority rather than at a bearer-token opencode, agentd becomes the policy point and C2's token degrades to an internal implementation detail no reading-of-which escalates anything. Until then, the enforcement tiers (Part D) deny-list `/proc`-typed reads and `/sandbox-cfg` paths for *tool-mediated* access, and the sweep proves the at-rest/env surfaces stay closed. **Upstream ask (ruled filed — §10-R1, batch item 1):** the session-ACL request is part of the four-ask upstream batch; it would close B3 without waiting for 0055's full arc.

### Part C — The admin token (#820-adjacent, same hygiene class)

`AGENTD_ADMIN_TOKEN` distinct-mode already prefers file delivery (`AGENTD_ADMIN_TOKEN_FILE` → `/sandbox-cfg/admin-token`). **r7 correction — the file is a uid-1000 surface in BOTH modes, not sidecar-uid-2000:** init-fs installs it 0400 whenever the Secret key exists, unconditioned on mode (`init_fs.go:209-214` — step 5 of the same run as the B1 w1 file), running as uid 1000 (`platform_init.go:62/69`) with the main container mounting `/sandbox-cfg` RO in the base build (`pod_builder.go:198`); `agentd_sidecar.go:23-24` states the uid-1000-files fact verbatim — which is WHY the sidecar consumer receives its copy via env (`AGENTD_ADMIN_TOKEN` secretKeyRef, `agentd_sidecar.go:110-115`): uid 2000 cannot read the 0400 uid-1000 file. Disposition, mode-split: (1) **single-container → file-only** (the `pod_builder.go:118` env wiring is the single-container main container; switch it to the file form — feasible, same uid); (2) **sidecar → env-only for the sidecar consumer is the existing, D1-correct design** (the "file form unconditionally" of earlier rounds was infeasible for this consumer and is withdrawn); the at-rest residual is therefore the **0400 uid-1000 file in BOTH modes** — declared, swept as a canary (§6.4b's sets include it in both mode rows).

### Part D — Enforcement (#825): the tiers are the floor, and this design says what they are and are not

The parked enforcement-tiers lane (`feat/opencode-permission-tiers` @ `e0f7ef23`) renders a platform-baked `permission` tier set into the harness config: **deny** on `/dev|/etc|/home|/proc|/root|/run|/sys|/var` (with sorted carve-outs), **credential-name denies** (`.git-credentials`, `auth.json`, `.secrets`, `.ssh`), **deny** on the resolved secret targets (`rt/auth.json`, `rt/secrets*`), **ask** ambient for `/sandbox-cfg`, `/sandbox-runtime`, `/home/sandbox`, and pre-allows for caches/config/workspace plus the `/tmp/*`, `/opencode/*`, and `/sys/fs/cgroup/*` carves. Its investigation also proved the prior soft gating was silently inert for months — the protection this issue originally assumed did not exist.

Disposition for #825: **the tiers are the enforcement floor, adopted as a dependency of this design** — but their honest scope is *tool-mediated* reads; arbitrary user-repo code opens files directly and no harness permission layer gates that (the 2026-08-14 verification's SEC-6 finding, unchanged). Therefore:

- **Fix (definition):** every credential the tiers deny-list is *also* structurally removed or mode-separated by Parts A–C. The tiers are defense-in-depth and the tripwire/audit surface (ask-tier events feed detection), never the load-bearing secrecy mechanism. This inverts the original #825 framing (from "policy as the defense" to "policy as the alarm around a defense that is structural").
- **#825 fix option 2's kernel-sandboxing arm (LANDLOCK/seccomp user-notification): DEFERRED to the upstream seam, dispositioned here (r1).** It is the one mechanism class that could bound Part D's own named residual (arbitrary-code reads of C4), and it cannot ship from this repo: the sandbox must be applied by the *pinned upstream harness binary* around its tool subprocesses — an upstream feature ask + pin bump, the same class as B2/Q5 and B3/Q1. Deferred with those (one upstream release could carry all three asks); the near-term bound on arbitrary-code C4 reads stays #821 egress.
- **Option 1's "default-deny unknown paths" vs the tiers' ask-ambient (rationale, r1):** default-deny-everything would break every workflow touching an unclassified path (any tool reading a new workspace location), and the tier set is platform-baked, not user-editable — a misclassification would be an outage, not a prompt. Ask-ambient keeps unclassified paths usable while the credential-bearing set — the paths that matter for THIS plane — is hard-denied by name. The tripwire value of ask-on-the-rest is the detection surface; default-deny's marginal secrecy over the named-deny set is zero for every credential in §2.
- **Option 3 (trusted-context instruction stripping): explicitly out of the credential plane's scope** — it defends the *decision* channel, not credential bytes. Deferred without a seam here; it belongs to the prompt-injection defense line (#819's SEC-class work), not this design.
- **Option 4 (outbound egress audit as the safety net), by name (r2):** adopted — it IS §6.3's exfil probes + R4's warn-only rolling metric + §5's gh/git channel rows, co-owned with #821 (D2). The detection net is the sweep's egress half plus the tiers' ask-tripwire; nothing rests on "the prompt says not to."
- **The #825 thread's recorded sequencing verdict ("SEQUENCE AFTER epic-72 … not independently actionable today") vs §7's tiers-first ordering, reconciled (r2):** the thread's verdict predates the tiers WIP and read "#825 action = the enforcement layer alone closing the issue." Under Part D's inversion, tiers-first is safe BECAUSE the tiers are the alarm, never the closure — early landing adds detection while epic-72 + this doc's parts do the closing. The thread's verdict is honored as "#825 does not close on tiers alone," which §7 asserts (step 1 carries no closure claim; closure is step 5's sweep).
- **Residual:** arbitrary-code reads of C4-class (user-owned) credentials remain possible; bounded by #821 egress and accepted in Part D2 below. Arbitrary-code reads of C2/C3 *files* in single-container mode remain possible (B1 residual).

### Part D2 — User-owned credentials (C4): presence by principal-design

git PATs, SSH keys, and env-secrets are the *user's own* material, delivered so the user's workflows work; the agent acts with the user's authority (design 0051 §3). Removing them from uid-1000 space would remove the product's git/ssh features. The design therefore accepts their presence and bounds their **exfiltration** (§5): to destinations the network policy permits (#821's allowlist mode, opt-in today), through channels the tiers' ask-tripwire observes (tool-mediated), with the honest statement that a determined same-uid agent with open egress can exfiltrate them — which is #821's problem, cross-referenced, and the reason #821 is co-prioritized (the 2026-08-27 staging comment's point 3 stands).

## 6. The proof: the credential-plane sweep (the #1500 bar)

One artifact closes all three issues' verification: **`local/credential-plane-sweep.sh`** (nightly-wired, both fleet modes), extending 0058's `agent_readable_files_keyfree` from "provider-key bytes" to "the plane":

1. **Canaries planted at the sources:** a distinctive provider key (staged via the real delivery path), the live workspace password, the admin token, a git PAT, a distinctive env-secret value.
2. **Read probes (every documented surface, including indirect):** full uid-1000 filesystem sweep (every path in §2 plus the symlink *names* and *targets*), `/proc/*/environ` and `/proc/*/fd` across all pod processes, the harness config re-read (`GET /config` post-restart), the auth-store restage (`PUT /auth` observer), the batch file (both modes), a **spawn-seam observer** asserting the REAL channels (r6): the PULL payload never contains the **C2 canary** (tautological of payload construction for C2 — `spawn_env_pull.go:173-183` serves exactly the parsed delta — pinned as a regression tripwire; NOT asserted for the C4 env-secret canary, which rides the payload BY DESIGN as the delivery path); the child's composed environ carries the canary **pre-A3 and not post-A3** (the w3 row — the load-bearing assertion); post-A3, the exec seam hands FD 3 (asserted via the child's `/proc` fd table in the boot window); and the password's only PULL-path appearance is the **w2 Basic-auth credential** (`spawn_env_pull.go:151-153` — asserted present in sidecar-mode supervisor environ per §6.4b's set, absent in single-container), and a memory row implemented per A8's feasibility spike: EITHER `/proc/<pid>/mem` where the runtime permits it, OR — the likely case — a **sweep-only build** of agentd that self-reports canary-presence from its own process memory (presence bits, never credential bytes) over the admin mux. **Build scoping (the r2 security constraint, load-bearing):** the memory-report primitive exists ONLY in a `sweep` build-tag binary variant that is never shipped to production pods — same source tree, separate CI-built artifact for the nightly/epic-exit runs; the production agentd binary must not contain the endpoint under any flag. Rationale: a flag-gated memory endpoint in the production binary would be a NEW credential-plane surface — and in sidecar mode a uid-1000→uid-2000 memory-read path across the 0051 boundary via the loopback-reachable sidecar mux (the spawn-env PULL pattern exactly). The proof artifact must not add what it proves absent.
3. **Exfil probes (the egress half):** from inside the workspace, attempt to send each canary to (a) an attacker-domain HTTP sink, (b) the provider's real endpoint with the canary as a key, (c) `gh api` with the PAT, (d) a git push with the PAT embedded. Assertions: (a) blocked-or-alerted when #821 allowlist mode is on, *observed-and-reported* when it isn't (the probe documents the open-egress residual rather than pretending), (b) 401 (nothing valid to present), (c)/(d) succeed-with-PAT **by design for C4 — the run reports them as the documented C4 residual, not a failure**, unless allowlist mode is on.
4. **Mode assertions:** sidecar-mode runs assert the w1-file absence (post-audit) and the w2 supervisor-environ PRESENCE; single-container runs assert the 0600 password file and the 0400 admin-token file, and the ABSENCE of any supervisor-environ canary (no container-env wire exists in that mode). Full sets per §6.4b.
4b. **Verdict semantics — a positive readability model, not bare absence (r1; probe-and-phase-aware r5):** the sweep's green is "no canary found *outside the declared residual set*," where the set is a function of THREE declared axes — **pod mode** (sidecar vs single-container), **A3 phase** (pre/post upstream FD-read), and **probe mode** (A8's P1/P2/P3, each with its own set). The base rows:
