# US-63.10: Fresh-Load Queue Visibility

**Epic:** 63 - Inboard Session Queue
**Priority:** High
**Depends on:** US-63.5 (SSE bridge), US-63.1 (spike)

## User Story

As a user who navigates to a session that already has messages queued (queued before I opened the page, or while I was viewing a different session), I want to see the queued-message pills immediately — not be blind to them until the next SSE event happens to fire.

## Background

This story exists because of a stress-test finding the original epic missed:

- US-63.5/US-63.6 derive queue pills from `queue.update` → `enqueued` SSE events.
- That model only works for messages admitted **during the page's lifetime** — the event is fired once and not replayed for a late-arriving viewer.
- The current `GET /sessions/:sid/queue` (`proxy_handlers.go:970`) solves this by listing the Redis queue on demand.
- **There is no V2 list endpoint in opencode 1.18.10.** The `session.pending.list` commit (`72992e00f`, "feat(core): session.pending.list API") is on the dev branch but not in the pinned tag. So if US-63.7 deletes `GET /queue` and there is no V2 replacement, fresh-load queue visibility is lost.

This is a real UX gap, not a theoretical one: a user with multiple sessions who queues a message in session A, switches to session B, and later returns to session A must see the pill.

## Acceptance Criteria

- [ ] A user navigating to (or refreshing) a session with pre-existing queued messages sees the pills without waiting for a new SSE event.
- [ ] The mechanism is chosen and documented: one of the options below.
- [ ] If a list endpoint is retained (Option A or B), it is feature-flag-aware and returns the V2-backed state under the flag.
- [ ] If the gap is accepted (Option C), the limitation is documented in CHANGELOG and the frontend shows a "queue state may be incomplete after refresh" hint when applicable.
- [ ] US-63.6's fresh-load handling and US-63.7's `GET /queue` deletion are gated on this decision.

## Approach Options (pick one in implementation)

| Option | Description | Pros | Cons |
|---|---|---|---|
| **A. Upstream `session.pending.list`** | Backport or bump to an opencode version that includes `session.pending.list`, expose it over HTTP, back `GET /queue` with it | Clean; authoritative source; matches the upstream direction | Requires opencode bump past 1.18.10 OR a backport PR; the endpoint may not be HTTP-exposed even on dev (verify in spike) |
| **B. Proxy-side shadow marker** | Keep a lightweight Redis set of `messageID`s admitted under `delivery: "queue"` (written on `enqueued` SSE, removed on `sent`); `GET /queue` reads it | No upstream dependency; works on 1.18.10; far smaller than the full `msgqueue` machinery (no text/retry/drain) | A second source of truth; must be kept in sync with opencode's durable rows; survives restart via Redis (good) |
| **C. Accept the gap** | Document that pills only appear for messages admitted during the page's lifetime; a refresh clears the view until the next event | Zero work | Real UX regression for multi-session users; may prompt support tickets |

**Recommendation: Option B** if the opencode bump (Option A) is not palatable. The shadow marker is a small, well-bounded use of Redis — it is *not* the deleted `msgqueue`; it holds only `{messageID, enqueuedAt}` tuples as a view-cache, with opencode as the authoritative source. If the marker and opencode diverge, opencode wins (the marker is best-effort).

## Assumptions

| # | Assumption | Validation |
|---|---|---|
| A1 | Multi-session users switching tabs is a real usage pattern worth supporting | Product/sponsor confirms. |
| A2 | Option B's shadow marker does not recreate the bug class the epic is deleting | The marker is read-only view state derived from opencode's events; it has no drain, no message-id generation, no retry, no abort interaction. It is strictly simpler than `msgqueue`. |

## Technical Details

Option B's marker can live in the existing `wsstate.Store` (Epic 45) — a Redis-backed `Set<messageID>` keyed per session, written from the US-63.5 SSE bridge when it synthesizes `enqueued`, cleared on `sent`. `GET /queue` returns the set with the cached text (if the marker stores text) or just IDs (frontend reconciles with history).

## Effort

Small (1 day) for Option B or C; Small-Medium (2 days) for Option A if a backport/bump is needed.
