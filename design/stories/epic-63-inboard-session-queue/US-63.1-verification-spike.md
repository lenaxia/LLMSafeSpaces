# US-63.1: Verification Spike — Confirm Bundled opencode Serves V2 Prompt + Interrupt

**Epic:** 63 - Inboard Session Queue
**Priority:** Critical
**Depends on:** —

## User Story

As the implementer, I want to confirm the bundled opencode binary (1.18.10) actually serves the V2 session endpoints end-to-end before I build proxy code against them — so that the rest of the epic is not built on an assumption.

## Background

Code reading (Epic 63 findings F2-F4) establishes that:
- `packages/protocol/src/groups/session.ts:205` defines `POST /api/session/:sessionID/prompt` with `delivery`
- `packages/opencode/src/server/routes/instance/httpapi/server.ts:177` mounts the V2 `Api`
- The TUI's `sdk.client.session.prompt` (`packages/sdk/js/src/v2/gen/sdk.gen.ts:5647`) calls exactly this route

But no llmsafespaces component has ever exercised these endpoints. Before US-63.2 builds a client, this spike confirms the contract against a real pod: response codes, body shapes, event emission, and the `delivery: "queue"` admission/drain cycle.

## Acceptance Criteria

- [ ] A kind workspace is brought up with the bundled opencode (1.18.10) and the following are exercised against its pod IP (Basic auth `opencode`+password):
  - [ ] `POST /api/session/:sid/prompt` with `{ prompt: { parts: [{ type: "text", text: "hi" }] } }` → returns success (record exact status + body)
  - [ ] `POST /api/session/:sid/prompt` with `{ ..., delivery: "queue" }` while the session is idle → admits and runs immediately (record status + body)
  - [ ] `POST /api/session/:sid/prompt` with `{ ..., delivery: "queue" }` while a turn is in flight → admits without error, does **not** return 409, and the message is processed after the in-flight turn (record status + body)
  - [ ] `POST /api/session/:sid/interrupt` during an in-flight turn → returns success, the running turn stops, and a subsequently-admitted queued message still runs (non-destructive)
  - [ ] `POST /api/session/:sid/interrupt` on an idle session → confirm whether it is a no-op success or an error (the proxy should treat both as success)
  - [ ] **OOM-restart drain (load-bearing for US-63.9):** queue a message with `delivery: "queue"` while a turn is in flight, then kill the opencode process (simulating OOM) and let agentd restart it. On restart + SSE reconnect, confirm whether the queued message drains automatically or strands until a new prompt arrives. Record the exact behavior — this determines whether US-63.9 needs the upstream `resume` endpoint or can accept the status quo.
- [ ] The SSE stream emits recognizable events for: prompt admitted, prompt promoted/run, turn start/finish, interrupt. **Expected per F13/F14:** the V2 events (`session.next.prompt.admitted`, `session.next.prompted`) arrive on the proxy's **existing `/event` subscription** (V1 route bridged from V2 via `EventV2Bridge`), NOT a separate `/api/session/:sid/event` stream. Record the actual type strings and a sample payload to confirm.
- [ ] A short spike report is written to `worklogs/` capturing: exact endpoint paths, status codes, body shapes, the event-type strings the proxy will subscribe to (feeds US-63.5), and the OOM-restart drain behavior (feeds US-63.9).

## Assumptions

| # | Assumption | Validation |
|---|---|---|
| A1 | The V2 prompt route uses the same Basic auth (`opencode` + workspace password) as V1 | This spike validates it directly. |
| A2 | `delivery: "queue"` does not return 409 when the session is busy (unlike V1 `prompt_async` which the proxy guards with its own 409) | This spike validates the busy case directly. |
| A3 | The V2 `PromptAdmitted`/`Prompted` events arrive on the proxy's existing `/event` SSE subscription (not a separate V2 stream) | **Pre-verified in code (F13):** the V1 `/event` route is bridged from V2 via `EventV2Bridge.Service`. The spike confirms it empirically against a live pod. |

## Technical Details

No production code changes. This is exploratory: a small Go test or a `curl`/`hurl` script run against a kind workspace pod. The `local/test.sh` harness already provisions a workspace with a known password.

The event-route question (A3) matters: the proxy's SSE tracker (`proxy_events.go`) currently subscribes to the V1 event stream. US-63.5 needs to know whether V2 `PromptAdmitted`/`Prompted` events arrive on the same stream or a different one. The spike answers this.

## Effort

Small (1 day). The value is de-risking the entire epic in a single day rather than discovering a contract mismatch mid-implementation.
