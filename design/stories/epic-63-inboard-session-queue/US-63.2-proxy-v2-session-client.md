# US-63.2: Proxy — V2 Session Client

**Epic:** 63 - Inboard Session Queue
**Priority:** Critical
**Depends on:** US-63.1 (spike confirms the contract)

## User Story

As the proxy, I want a thin V2 session HTTP client that can send a prompt with `delivery` and issue an interrupt — so that US-63.3 (enqueue) and US-63.4 (abort) can use it instead of the V1 `prompt_async`/`abort` paths.

## Background

The proxy currently reaches opencode via V1 paths through `pkg/agent/opencode/` (Epic 29's `AgentClient` abstraction) and `proxy_input.go`. The V2 endpoints live at `/api/session/:sid/prompt` and `/api/session/:sid/interrupt` on the same listener, same Basic auth (Epic 63 F5). This story adds the client; the migration of call sites is US-63.3/63.4.

## Acceptance Criteria

- [ ] A new V2 session client exists in `pkg/agent/opencode/` (e.g. `client_v2.go`) with:
  - [ ] `PromptV2(ctx, workspaceID, sessionID, body)` where `body` carries `prompt` (parts) and optional `delivery: "steer"|"queue"` and `resume`
  - [ ] `InterruptV2(ctx, workspaceID, sessionID)`
- [ ] **The client OMITS the `id` field on prompt** (Epic 63 F17). opencode generates the message ID via `SessionMessage.ID.create()`; a caller-supplied `id` risks `PromptConflictError` (409) on collision — the same class of bug as the existing message-id hack, avoided by simply not sending one.
- [ ] Both methods resolve the pod IP + password via the existing `getPodIPAndPassword` helper (no new auth path)
- [ ] Both POST to `/api/session/:sid/prompt` and `/api/session/:sid/interrupt` respectively, with Basic auth header `opencode`+password, matching the spike's confirmed contract (US-63.1)
- [ ] The request body uses the V2 shape `{ prompt: { parts: [...] }, delivery, resume }` — NOT the V1 shape `{ parts, messageID }` (the two are incompatible)
- [ ] Methods are feature-flag aware: a `v2SessionQueueEnabled` config/flag accessor exists, but the client itself is just transport — the flag is checked at call sites in US-63.3/63.4
- [ ] Unit tests (mocked HTTP transport) cover: success status, 409 `PromptConflictError` mapping (in case opencode ever generates a colliding id), 404 `SessionNotFound` mapping, auth header correctness, path construction
- [ ] No change to the V1 client paths — V1 and V2 clients coexist until US-63.7 deletes V1 call sites

## Assumptions

| # | Assumption | Validation |
|---|---|---|
| A1 | The V2 prompt success response is non-streaming (admit-and-schedule), so the proxy can read+discard the body and return | US-63.1 spike records the exact status/body. If streaming, this story adds a drain-and-discard step (the proxy already does this for other V1 streaming routes). |
| A2 | Pod IP + password resolution is identical for V1 and V2 (same listener, same Basic auth) | Epic 63 F5; US-63.1 spike confirms. |

## Technical Details

Follow the existing `pkg/agent/opencode/client.go` and `proxy_input.go:169` patterns for pod-IP resolution and Basic auth. The only deltas are the path (`/api/session/...` vs `/session/...`) and the request body shape (`{ prompt: {...}, delivery, resume }` vs V1 `{ parts, messageID, ... }`).

No Go SDK is generated for opencode's V2 API; this is a hand-written thin client against the documented contract (Epic 63 F12, Non-Goal).
