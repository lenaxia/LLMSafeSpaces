# US-63.4: Abort Path — Non-Destructive `interrupt`; Remove Queue Clear + flushAndAbort

**Epic:** 63 - Inboard Session Queue
**Priority:** High
**Depends on:** US-63.2 (V2 client)

## User Story

As a user who aborts a session, I want the in-flight turn to stop but my queued messages to survive and run on resume — so that "stop" means "stop now," not "discard everything I queued."

## Background

Today, `AbortSession` (`proxy_handlers.go:625`) proxies to V1 `/abort`, then `PeekAll`+`Clear`s the Redis queue, emits `dismissed` SSE for each, and asynchronously runs `flushAndAbortAfterIdle` (`:674-750`) — a 75-line routine that re-sends each flushed message one-at-a-time and aborts again so they appear in the transcript unprocessed. This entire workaround exists because the external queue cannot survive an abort.

opencode's V2 `POST /api/session/:sid/interrupt` is non-destructive (Epic 63 F8): it kills the running fiber and fails open tools/assistant, but **preserves** admitted-but-unpromoted input rows; the next `resume` (triggered by the next prompt or session activity) re-drains them. The proxy's abort becomes a one-line forward.

## Acceptance Criteria

- [ ] `AbortSession` (when `v2SessionQueueEnabled`): calls `client.InterruptV2(...)` instead of V1 `/abort`. The `PeekAll`+`Clear` and `flushAndAbortAfterIdle` calls are **bypassed** under the flag.
- [ ] Under the flag, abort does **not** emit `dismissed` SSE for queued messages (they are not dismissed — they survive). Acceptance: a queued message present at abort time is still processed after the session resumes.
- [ ] `flushAndAbortAfterIdle` (`proxy_handlers.go:674-750`) is unreachable under the flag; deleted in US-63.7.
- [ ] `ForceAbortSession` (Epic 44 admin escape hatch, `admin_session.go:19`) is **untouched** — it operates on stuck pods, a different concern.
- [ ] E2E test (feature-flagged): queue 2 messages → abort mid-turn → both queued messages run after resume (matches opencode's `session-runner.test.ts:1901` "preserves durable queued input for a later wake after interruption").
- [ ] Existing abort tests (`proxy_queue_test.go:704+`) still pass under flag-off (legacy destructive path).

## Assumptions

## Technical Details

The flag check sits at the top of `AbortSession`. Under the flag, the flow is: `client.InterruptV2(...)` → return. No queue mutation, no background goroutine.

The spike (US-63.1) confirms whether `interrupt` returns success for an idle session (no-op) vs an error — the proxy should treat both as success (abort is idempotent from the caller's perspective).
