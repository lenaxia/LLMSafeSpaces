# US-63.9: Stranded-Input Recovery — Drain Queued Input After Pod Restart

**Epic:** 63 - Inboard Session Queue
**Priority:** Critical
**Depends on:** US-63.3 (enqueue migrated), US-63.1 (spike confirms V2 contract)

## User Story

As a user whose workspace pod restarted (OOM, kill, rolling update) while I had messages queued, I want those queued messages to drain automatically when the pod comes back and I reconnect — so that they are not silently stranded until I happen to type something new.

## Background

This story exists because of a stress-test finding (Epic 63 F15-F16) that the original epic missed:

- opencode's V2 runner drains queued input only when `runner.run` is triggered, and `run` is triggered **only** by `execution.wake` (on a new prompt) or `execution.resume`.
- **`resume` is not exposed in the V2 HTTP API** (F15). The only session endpoints are `prompt, interrupt, wait, compact, ...` — no `resume`. `session.wait` is a stub returning `OperationUnavailableError`.
- **Nothing auto-drains on pod startup** (F16). opencode's durable `SessionInput` rows survive in SQLite, but nothing scans for them on boot.

Today, the proxy's `reconcileSessionState` stranded-queue sweep (`proxy_events.go:652-663`) handles this: on SSE reconnect it finds idle sessions with non-empty Redis queues and re-triggers `drainQueuedMessage`. Once the Redis queue is deleted (US-63.7), that sweep has nothing to drain — and there is no V2 equivalent to call. Queued input would strand until the user's next prompt.

This story closes that gap **before** US-63.7 deletes the sweep.

## Acceptance Criteria

- [ ] A mechanism exists so that, after a pod restart, an idle session with pending V2 `SessionInput` rows drains them without requiring the user to send a new prompt.
- [ ] The mechanism is triggered from the proxy's existing `reconcileSessionState` reconnect path (replacing the deleted stranded-queue sweep), OR from opencode's startup, OR via a periodic poll.
- [ ] E2E test: queue 2 messages → kill the opencode process (simulating OOM) → wait for restart + SSE reconnect → both queued messages drain and run, with no new user prompt.
- [ ] The mechanism does not double-run messages (idempotent against opencode's own admission/drain).
- [ ] US-63.7's deletion of the stranded-queue sweep is gated on this story's completion.

## Approach Options (pick one in implementation)

| Option | Description | Pros | Cons |
|---|---|---|---|
| **A. Upstream `resume` endpoint** | Contribute a small PR exposing `POST /api/session/:sid/resume` in `packages/protocol` + `packages/server`, wiring to the existing `SessionV2.resume()` (`session.ts:426`). The proxy's reconnect path calls it for idle sessions. | Clean; uses the core API already built for this; no proxy-side hack; matches the `resume` semantic opencode intended | Small upstream PR cycle (this is a *real* gap, unlike the false "expose V2" premise from the first draft) |
| **B. Proxy-side wake via empty prompt** | On reconnect, for idle sessions, POST a `delivery: "queue"` prompt with empty/no-op text to trigger `wake` → `run` → `hasPending` drains | No upstream change; works today | Pollutes history with a no-op user message; opencode may reject empty prompts (needs spike confirmation) |
| **C. Accept the regression** | Document that queued messages strand after a pod crash until the next user prompt | Zero work | Reintroduces the bug class Epic 41's sweep fixed; poor UX for an OOM-prone workload |

**Recommendation: Option A.** It is a genuine upstream gap (the core `resume` exists and is HTTP-exposed for the TUI/SDK via... actually it isn't — confirm in the spike whether the TUI triggers resume through some other path). The PR is small and well-scoped. Option B is the fallback if the upstream cycle is too slow.

## Assumptions

| # | Assumption | Validation |
|---|---|---|
| A1 | opencode's `SessionV2.resume()` (`session.ts:426-428`) is safe to call on an already-idle session (no-op if nothing pending) | `coordinator.run` (`run-coordinator.ts:67-79`): if idle and no pending, returns immediately. Safe. |
| A2 | The pod's SQLite (on the PVC at `XDG_DATA_HOME=/workspace/.local`) survives the restart so the `SessionInput` rows are still there | `runtimes/base/tools/entrypoints/entrypoint-opencode.sh:13` sets `XDG_DATA_HOME=/workspace/.local` which is on the persistent PVC. Confirm in the spike. |
| A3 | The proxy can identify "idle session with pending input" without a V2 list endpoint (none exists in 1.18.10) | Tracked: the proxy either (a) keeps a lightweight Redis marker of "sessions that received a queue delivery since last drain," or (b) the upstream `resume` endpoint returns whether it drained anything. Option (a) is a thin shadow of the current queue — far smaller than the full `msgqueue` machinery. |

## Technical Details

Option A's upstream change is ~15 lines across `packages/protocol/src/groups/session.ts` (add `HttpApiEndpoint.post("session.resume", "/api/session/:sessionID/resume", ...)`) and `packages/server/src/handlers/session.ts` (add `.handle("session.resume", ...)` calling `session.resume(sessionID)`). The core `SessionV2.resume` already exists.

If Option A is chosen, this story carries a real (small) upstream dependency — flag it in the parallelization plan. If Option B/C, no upstream dependency.

## Effort

Medium (3 days). Most of the effort is the e2e OOM-restart test and the proxy reconnect-path rewrite; the upstream PR (Option A) is small but adds review latency.
