# US-63.8: SDK Coordination — Align Epic 62 US-62.6 Queue Methods with V2 Model

**Epic:** 63 - Inboard Session Queue
**Priority:** Normal
**Depends on:** US-63.3 (enqueue migrated; V2 contract stable)

## User Story

As an SDK consumer, I want the queue methods in all four SDKs to reflect the new V2-backed model — so that I am not building against an API surface that is about to change or be removed.

## Background

Epic 62 US-62.6 adds `enqueue` / `listQueue` / `dismissQueued` / `markSeen` to the TS/Python/Go/Java SDKs against the current Redis-backed API (`proxy_handlers.go:907-1028`). Epic 63 changes that surface:

- `enqueue` now hits the V2-backed path (same `/queue` endpoint shape, but the underlying durability/abort semantics differ).
- `dismissQueued` is **removed** (US-63.7) — abort is non-destructive and there is no revoke.
- `listQueue` is **removed** in US-63.7 unless US-63.10 retains it; the queue list otherwise derives from SSE events.
- `QueuedMessage` struct fields (`retry_count`, etc.) lose meaning under V2.

If Epic 62 lands first, US-62.6 ships SDK methods that are immediately partially obsolete. This story coordinates the two epics.

## Acceptance Criteria

- [ ] The Epic 62 US-62.6 story is updated to document the V2 impact: `enqueue` remains; `dismissQueued` and `listQueue` are deprecated/removed pending US-63.7/US-63.10.
- [ ] If US-62.6 has already shipped SDK methods: `dismissQueued` and `listQueue` are marked `@deprecated` in this release with a pointer to the V2 model; removed in the next major.
- [ ] The SDK `QueuedMessage` type is documented as best-effort under V2 (fields like `retry_count` are vestigial).
- [ ] The SDK parity matrix in Epic 62's README reflects the post-Epic-63 surface.
- [ ] A note is added to `sdks/README.md` explaining that queue list/dismiss are not part of the long-term V2 model and showing the event-derived alternative for SDK consumers who need a list.
