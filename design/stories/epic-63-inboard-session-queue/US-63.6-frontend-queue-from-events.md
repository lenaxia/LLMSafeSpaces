# US-63.6: Frontend — Derive Queue State from Events; Remove Drain-on-Idle

**Epic:** 63 - Inboard Session Queue
**Priority:** High
**Depends on:** US-63.5 (SSE bridge emits the same `queue.update` events), US-63.10 (fresh-load visibility decision)
**Status:** Complete — no code changes required (see Verification below)

## User Story

As the frontend, I want queue pills to appear and disappear based purely on the SSE events I receive — so that I no longer need the `useMessageQueue` drain-on-idle logic that races with opencode's own draining.

## Background

Today the frontend `useMessageQueue` hook (`frontend/src/hooks/useMessageQueue.ts`) holds queued messages client-side and drains them via `notifyIdle()` on each `session.status=idle` SSE event. This client-side drain is the source of Epic 41's bugs (the `reconcileOnIdle` streaming-state clear timing, the 409 retry path).

Under V2, opencode owns draining entirely. The frontend's job reduces to: render pills for messages that have been admitted (`enqueued`) but not yet promoted (`sent`), and remove them when `sent` arrives (or when the message appears in history). No client-side drain, no `notifyIdle`, no retry counter.

## Acceptance Criteria

- [ ] When `v2SessionQueueEnabled` is active server-side, the frontend does **not** call `notifyIdle()`/`drainOne()` — queue messages are not held client-side for re-sending.
- [ ] Queue pills are derived from `queue.update` → `enqueued` events; a pill is removed when `queue.update` → `sent` arrives for that message ID (or when the message appears in fetched history).
- [ ] The `mark_pending` / `mark_error` / `_retryCount` machinery from Epic 41 US-41.3 is bypassed (no 409s exist under V2).
- [ ] The submit path: when the user submits while busy, the frontend POSTs to `/queue` (or `/prompt`); the message is added to the local pill list **optimistically** and confirmed by the subsequent `enqueued` event from the server.
- [ ] **Fresh-load case is handled per US-63.10** (a user landing on a session with pre-existing queued messages must see the pills — either via a retained list endpoint or an accepted gap).
- [ ] No regression in the flag-off path: the existing `useMessageQueue` drain logic still runs when the server is in legacy mode.
- [ ] Tests cover the event-derived path: enqueue → pill appears; `sent` → pill removed; `sent` arriving before local optimistic add → no fl.
- [ ] US-41.1's `reconcileOnIdle` streaming-clear fix is **unaffected** (it remains correct and necessary regardless of queue source).

## Assumptions

| # | Assumption | Validation |
|---|---|---|
| A1 | The server can signal to the frontend which mode it is in | Via an existing feature-flag/config endpoint, or by always deriving from events once US-63.5 ships. |
| A2 | Removing client-side drain does not regress the multi-tab case | Under V2, the queue lives in opencode, so two tabs both see the same `enqueued`/`sent` events on the workspace SSE stream. The client-side drain (inherently single-tab) is not a correctness feature under V2. |

## Verification (2026-08-10)

**No code changes required.** The story spec described Epic 41's original
client-side drain-on-idle architecture (`notifyIdle`/`drainOne`/`_retryCount`).
Inspection of the current frontend reveals that machinery was already removed
in a prior refactor — `useMessageQueue.ts` is purely event-driven:

- Pills are derived from `queue.update` SSE events via `refreshQueue()` (which
  calls `GET /queue` and reconciles).
- No `notifyIdle`, `drainOne`, or `_retryCount` exists in `frontend/src/`.
- Fresh-load is handled by `refreshQueue()` on mount (calls `GET /queue`).
- Under V2, the SSE bridge (US-63.5) synthesizes the same `queue.update`
  events, and the shadow marker (US-63.10) backs `GET /queue` — the frontend
  is mode-agnostic; it works identically under V1 and V2.

All acceptance criteria are met by the existing event-driven architecture.
The `reconcileOnIdle` streaming-clear fix (US-41.1) is in `useChatStream.ts`
(not `useMessageQueue.ts`) and is unaffected.
