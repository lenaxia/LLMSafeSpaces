# US-63.5: SSE Bridge — Map V2 `PromptAdmitted`/`Prompted` → `queue.update` Events

**Epic:** 63 - Inboard Session Queue
**Priority:** High
**Depends on:** US-63.2 (V2 client), US-63.1 (spike records event-type strings)

## User Story

As the frontend, I want the same `queue.update` SSE events (`enqueued`, `sent`) I receive today — so that the queue pill UX works without a frontend rewrite — even though the source of those signals is now opencode's V2 event stream rather than the proxy's Redis queue.

## Background

Today the proxy emits `queue.update` events from three sites:
- `EnqueueMessage` → `enqueued` (`proxy_handlers.go:947-956`)
- `drainQueuedMessage` → `sent` (`proxy_events.go:494`) and `error` (`:480`)
- `AbortSession` → `dismissed` (`proxy_handlers.go:659-661`) — removed by US-63.4

Under V2, opencode emits its own events on the session event stream:
- `SessionEvent.PromptAdmitted` (input admitted, `promoted_seq` null) — the "enqueued" signal (Epic 63 F9, `input.ts:54-61`)
- `SessionEvent.Prompted` (input promoted, `promoted_seq` set) — the "sent"/"running" signal (Epic 63 F9, `input.ts:225-231`)

The proxy's SSE relay (`onRawEvent`, `proxy_events.go:176`) already forwards every opencode event to the frontend as `opencode.event`. This story translates the V2-specific types into the existing `queue.update` taxonomy so the frontend is unchanged.

## Acceptance Criteria

- [ ] When `v2SessionQueueEnabled`, the proxy's raw-event handler (`onRawEvent` or a dedicated dialect hook) detects V2 `PromptAdmitted` events with `delivery: "queue"` and emits a synthesized `queue.update` → `enqueued` SSE event with the message ID.
- [ ] It detects V2 `Prompted` events for queue-delivery inputs and emits `queue.update` → `sent`.
- [ ] The synthesized events use the exact same `queueUpdateData` shape (`{ event, messageID, error? }`, `frontend/src/api/types.ts:283`) as today.
- [ ] Under the flag, `EnqueueMessage`/`SendPromptAsync` no longer emit `enqueued` themselves (US-63.3) — the event is derived purely from the V2 `PromptAdmitted` event, eliminating the race where `enqueued` fires before opencode has actually admitted.
- [ ] The `error` variant is mapped from any V2 admission failure event (if the spike identifies one); if V2 admission is atomic and infallible (expected per F8), `error` is never emitted under the flag.
- [ ] Unit tests cover the event-type → `queue.update` mapping using sample payloads from the US-63.1 spike.

## Assumptions

| # | Assumption | Validation |
|---|---|---|
| A1 | The V2 `PromptAdmitted`/`Prompted` events arrive on the same SSE stream the proxy already subscribes to (the V1 event relay path) | US-63.1 spike records the event route and type strings; this story consumes that. |
| A2 | The event payloads carry enough to synthesize `{ event, messageID }` (specifically the message ID and the delivery field) | `packages/schema/src/session-event.ts:94-99` (`PromptAdmitted` carries `messageID`, `prompt`, `delivery`); spike confirms the wire shape. |
| A3 | opencode emits exactly one `PromptAdmitted` per admitted input and one `Prompted` per promoted input (no duplicates) | `packages/core/src/session/input.ts:54-61, 225-231` — single publish per transition. |

## Technical Details

The mapping belongs in the existing `dialect` hook (`emitNormalizedInputEvent`, `proxy_events.go:234`) or a sibling normalizer — the same place question/permission events are translated. The dialect layer is the natural home for opencode-version-specific event shaping.

The `dismissed` variant is **not** synthesized under the flag (US-63.4 removes the destructive clear). If a future upstream `SessionInput.revoke` is adopted, `dismissed` can be re-derived from a revoke event then.
