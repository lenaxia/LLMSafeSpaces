# US-71.3a — Unanswered-question inbox

**Issue:** [#1313](https://github.com/lenaxia/LLMSafeSpaces/issues/1313) · **Epic:** [#1314](https://github.com/lenaxia/LLMSafeSpaces/issues/1314) (stream 3a) · **Spec:** [#1312](https://github.com/lenaxia/LLMSafeSpaces/issues/1312)

**Status:** in implementation (design recreated 2026-09-12 after the original
design branch was lost with its claim; the three design decisions survive from
the reclaimed claim record, issue #1314 comment 5626073609).

## Problem

The agent asks a question mid-turn (question tool or permission ask). The user
is away. The ask times out or the pod recycles, the turn wraps up, and the ask
is gone. On return the user sees a cancelled question and a dead end; the only
path forward is typing "please ask me the question again" and burning a turn
re-establishing context the platform already had.

## Design

A durable, platform-owned **inbox** per workspace:session — the outbox's
sibling for inbound asks. API/Redis-side, so it survives workspace
suspension/resume (pod state does not).

1. **Record at ask time.** When an ask is surfaced to a browser it is recorded
   in the inbox store (kind, question text/options, permission/patterns, tool
   context, session). The live harness ask remains just the doorbell — timeout
   may kill it freely.
2. **Re-present on return.** The snapshot flight (D9/D10 machinery) renders
   pending UI = live asks (lease, #1310) ∪ inbox records. An inbox-only record
   renders as "While you were away, the agent asked: …" (`whileAway`-tagged)
   with the original choices still clickable.
3. **Late answer lands in history.** Answering a non-live ask composes a Q&A
   user message — original question plus the answer — enqueued through the
   standard outbox path (one delivery regime, S1/S2 intact). The model sees
   the Q&A pair in context and continues; no re-ask. Works from any device.
4. **Dismiss is a first-class exit.** Dismissal clears the record. Every inbox
   record has exactly two exits — answered-in-history or dismissed (S11).
5. **Permissions default safe.** A permission ask that times out is
   *not granted* (the harness already denies the tool call). Workspaces with
   `autoApprovePermissions` bypass the inbox as they bypass prompts today.

### Carried decisions (from the reclaimed design)

1. **Terminal records update in place.** Answered/dismissed set a terminal
   status on the record rather than deleting it; the snapshot union and any
   duplicate resolution event consult the status. A duplicate
   `INPUT_RESOLVED` (e.g. agentd replay after API rollover) cannot resurrect
   a cleared prompt — S11 becomes mechanical, not event-ordering-dependent.
2. **Dismiss on a live ask rejects the live ask first.** Dismissal of a
   record whose ask is still live in the harness rejects the harness ask
   (question/reject · permission reply "reject") before clearing the record.
   Otherwise the two-exits invariant has a hole: dismissed record + still
   ringing doorbell.
3. **Snapshot-path record upsert.** Records are (re-)written from the
   snapshot flight's `ListPending` results too, not only from live
   `InputRequested` events — events are droppable (busy-gated stream, broker
   replay bounds); the snapshot path is the recovering write. Upsert by ask
   identity; no duplicate records per ask ID.

## G1 evidence — timed-ask behavior on the pinned opencode 1.18.15

Local `opencode serve` (the pinned binary) + scripted OpenAI-compatible mock
provider; basic auth `opencode:<pw>`; `OPENCODE_EXPERIMENTAL_EVENT_SYSTEM=true`
(per testdata/REFRESH.md procedure). Scratch serve, no cluster.

| Observation | Evidence |
|---|---|
| `question` tool schema | `GET /experimental/tool?provider=mock&model=mock-1` → parameters are `questions: [{question, header, options: [{label, description}], multiple}]` — **no timeout parameter on the tool** |
| No config-level question timeout | `opencode-config.schema.json`: the only `question` key is a permission action rule (`ask`/`allow`/`deny`); no timeout setting exists |
| Pending question does not self-expire | An unanswered `question` ask stayed in `GET /question` with tool part `status:"running"` for the full 26-minute observation window: the turn hangs on the ask; nothing wraps up on its own |
| Pending permission does not self-expire | An unanswered permission ask stayed in `GET /permission` for 24 minutes — no auto-grant, no auto-deny, no expiry event. Not-granted is structural: an abandoned ask grants nothing |
| Reject path → model-visible terminal state | `POST /question/{id}/reject` → tool part state becomes `status:"error", error:"The user dismissed this question"`; the turn ENDS (step-finish) with **no second provider call** |
| Reply path → model-visible answer | `POST /question/{id}/reply {"answers":[["…"]]}` → provider re-invoked with tool result text: `User has answered your questions: "<question>"="<answer>". You can now continue with the user's answers in mind.` |
| Permission reject → not-granted state | `POST /permission/{id}/reply {"reply":"reject"}` → tool part `status:"error", error:"The user rejected permission to use this specific tool call."`; no second provider call |
| Permission ask shape | `permission.asked`/`GET /permission` carries `{id per_…, sessionID, permission:"bash", patterns, metadata{command}, always[], tool{messageID, callID}}` — matches the dialect pin |

Captured as `pkg/agent/opencode/testdata/ask_terminal_states_1_18_15.json` (provenance + redactions in-file).

**Implication for #1313's premise:** on the pinned version the *question tool
itself* never times out — the "ask times out, turn wraps up" incident class
comes from the surrounding platform (turn/session aborts, pod recycle,
agentd's lease resolve-by-absence when the harness registry drops the ask, or
the user aborting a wedged turn), not from an opencode question timer. The
inbox design is unchanged (it does not care why the live ask died), but the
walk-away E2E must simulate the ask's death via the platform's own mechanisms
(abort / lease drop / suspend), not wait for a harness timer.

## G2 — Q&A framing

Validated by construction from G1: the harness's own answer framing is plain
text (`User has answered your questions: "…"="…". You can now continue…`) and
the dismissed framing is the tool-error string above — a late-answer user
message in the same register ("Answering your earlier question: …") composes
with both. A live-model confirmation turn rides the walk-away E2E leg (the
in-repo harnesses run against the scripted mock; asserting the model's
continuation quality requires the real model, which only the pool/staging
legs exercise). Recorded as a deferred gate, not a silent drop.

## Architecture (as-built plan)

### Inbox store (`api/internal/services/inbox`)

Redis-backed, beside the outbox's key family:

- `inboxq:{ws}:{ses}` — HASH keyed by ask ID → JSON `Record` (a hash, not a
  list: per-record terminal updates in place without O(n) rewrites).
- TTL on the whole key (proposed 24h, matching `outboxdedupe`) so abandoned
  sessions cannot accumulate forever; per-session cap of 10 pending records,
  FIFO eviction of the oldest pending record.
- `Record{ID, SessionID, Kind, Question, Header, Options, Multiple, Custom,
  Permission, Patterns, Always, Tool, RecordedAt, Status(pending|answered|
  dismissed), StatusAt}` — mirrors `session.InputRequest` (typed struct, not
  a map; Rule 1).
- Operations: `Record` (upsert-if-absent-or-pending; terminal records are
  immutable), `Resolve(id, status)` (pending → terminal, in place),
  `List(workspaceID, sessionID) → pending records`, plus internal eviction.
- Constructed like the outbox: `New(client *redis.Client) *Service`, nil when
  client nil; wired in the app's cache block; handler setter
  `SetInboxStore` + `SetInboxStoreForTest`.

### Write paths (decision 3)

- **Live:** `usageBridge.InputRequested` (proxy_usagestream.go:200) records
  every surfaced ask after publishing the SSE event (permission asks under
  auto-approve are not recorded — they never surface).
- **Snapshot:** `emitPendingViaAdapter` (proxy_input.go:241) upserts records
  for every pending ask the flight observes (the recovering write under
  droppable events).
- **Resolution:** `usageBridge.InputResolved` deliberately does NOT touch
  the record — resolution is a liveness signal, not a disposition (it
  fires for answered, timed-out, dropped, and lease-resolved asks
  alike). Only the reply/reject routes terminalize: proxy success ⇒
  answered/dismissed. Otherwise the walk-away record would clear on the
  very timeout it exists for.
- **Liveness is tri-state** (`askLivenessOf`: live / dead / unknown).
  Unknown (unreachable harness — the suspended window) degrades the
  REPLY path to the late-answer flow (an answer is safe against a
  possibly-live ask by construction) but fails the DISMISS path CLOSED
  (503): terminalizing a possibly-ringing ask reopens the two-exits hole
  irreversibly (terminal records are immutable).
- **Union under harness failure:** a `ListPending` failure still emits
  the inbox half of the snapshot union with the ok=false marker
  (non-authoritative; clients never wipe live prompts) — the whileAway
  re-presentation survives the suspension window, the exact scenario
  the inbox exists for.

### Snapshot union (S5 extension)

`emitPendingViaAdapter` emits live pending (as today) **plus** inbox records
whose ask ID is not in the live set, tagged `whileAway: true` on the event's
request payload (additive field on the legacy wire shapes — the frontend
prompt components key on it for the "While you were away" variant).

### Late answer (L8)

`QuestionReply`/`PermissionReply` (proxy_input.go) gain a pre-proxy step:
if the ask is not live (proxy 404 / not in the pending set), the handler
composes the Q&A user message and `outbox.Accept`s it (cmid
`inbox-{askID}-answer`), marks the record answered, and returns 202. The
model continues with the Q&A pair in transcript context. S2 applies to the
composed entry exactly as to any user message (messageID = `msg_ + entryID`
at the harness write — 0a's contract).

Q&A message text (framed from G1 evidence):

```
Answering your earlier question — "<question>" (<option labels joined>):
"<answer>"
```

For permissions: `Permission decision on "<permission> <patterns>": <once/
always/reject>` — a late "once/always" is still delivered as information to
the model (the original tool call already terminated not-granted); it does
NOT retro-grant anything (G1: pending permission asks do not outlive their
turn's context; see register A8).

### Dismiss (S11)

New REST route `DELETE /workspaces/:id/sessions/:sessionId/inbox/:requestID`
(+ frontend wiring). If the ask is still live in the harness: reject the live
ask first (decision 2), then `Resolve(dismissed)`. Dismissal of an already
terminal record is idempotent 204. A light `queue.update`-style SSE event
(`agent.question.resolved` shape, additive `data.reason="dismissed"`) clears
other tabs' UI.

### Permissions timeout = not granted

No harness change: the pending permission ask terminates with the turn that
raised it (G1 watch); the tool call's terminal state is the harness's denial
(A8). The inbox record + late-answer-as-information is the only addition.

## Test plan (README §0)

**Unit (inbox store):** record/upsert lifecycle; terminal immutability
(duplicate resolve cannot resurrect); cap eviction; TTL; list filtering;
store-reconnect survival. Multiple happy + unhappy paths.

**Unit (handlers):** snapshot union (live ∪ inbox, no dupes by ask ID,
whileAway tag, auto-approve filtering); InputRequested recording incl.
auto-approve non-recording; InputResolved KEEPS the record pending (the
liveness/disposition split); late-answer composition (question +
permission variants); dismiss (live-first reject, unknown-liveness
fail-closed, idempotent, contention); union emission under both
`ListPending` and `ListWorkspace` failures.

**Integration:** connect-time re-presentation end-to-end (SSE flight includes
inbox); late answer routes through the outbox exactly once (S2 dedupe key
`inbox-{askID}-answer`); dismiss clears everywhere.

**E2E (kind, `local/`):** walk-away — ask raised, turn aborted (platform
mechanism), browser reconnects, prompt re-presents whileAway, answer
lands in the delivery payload with question + answer (the
model-continuation half — "the assistant's next turn references the
answer, not a re-ask" — needs a real model and rides the staging leg;
recorded deferral, not a silent drop). Suspend/resume variant: suspend
between ask and return; inbox survives (L7 ≤2s re-presentation
asserted). API-rollover-mid-answer state (marker present, record still
pending) → re-POST converges (S11 never-lost).

**Fault legs:** API rollover mid-answer — S11 holds (answered exactly
once via outbox dedupe or still pending, never lost); duplicate
INPUT_RESOLVED — no resurrection (terminal immutability).

**Frontend:** vitest for the WhileYouWereAway variant (answer, dismiss,
stack); Playwright walk-away-walk-back leg (route-mock strategy — the
provider stores whileAway content from user-stream events; ChatPage's
contract-fold removal exempts whileAway prompts, which the pod fold
never carries by design).
