# Image Factory — custom workspace images

**Author:** design session 2026-08-01 (revised 2026-08-02 — abstraction-level pass)
**Status:** Approved (design — no implementation yet)
**Related:** `pkg/apis/llmsafespaces/v1/runtimeenvironment_types.go`, `design/archive/v1/0007_2025-03-05_runtimeenv.md` (legacy multi-image model, superseded), Epic 7 (runtime interception — closed, incompatible)

> **What changed in this revision (and why).** An earlier draft modeled catalog
> extensions as *editable* rows and spent machinery (frozen snapshots, a
> separate blocklist table keyed on extension IDs, 3-attempt retry semantics)
> patching the inconsistency that editability created. That was the wrong level
> of abstraction. **Extensions are immutable published artifacts** — you don't
> edit what "python313" means, you publish `python314` and retire the old one
> (apt-track versioning is superseded by ruling #29 below — the base is the
> version axis there). This
> single change dissolves the snapshot/blocklist/retry complexity by
> construction. The failure path is also re-leveled: apt builds succeed ~99%
> of the time, so one transient retry + a single `known_failures` row replaces
> the 3-attempt machinery. Build status is derived on read rather than
> background-polled, which makes the "no standalone service" decision trivially
> true. No user-facing capability is lost.

## Problem

Workspaces run a single blessed base image (`runtimes/base`, Debian
bookworm). Users and agents occasionally need dependencies the provided
package managers (`mise`/`pip`/`npm`/`go`) **cannot** supply — system
libraries (libgl, libssl, CUDA, ODBC), vendored binaries, proprietary CLIs,
or one-off system setup. Today there is no path for a user to get those into
their workspace image. The motivating symptom was a binary that failed to
start with a missing libc; that is one instance of the general gap.

We need a way for users (within authorization) to obtain workspace images
that extend an operator-approved base with extra dependencies — without
exposing a free-text injection surface, without storing secrets in images,
and without requiring platform operators to hand-build a new image per
request.

## Non-goals

- **No secrets in images or schematic hashes.** Credentials stay in the
  existing injection path (K8s Secrets, never baked into image layers).
- **No free-text user input into the build.** Schematics are a *selection*
  of catalog item IDs, never arbitrary commands/files. This eliminates the
  injection / arbitrary-code-execution-on-builders surface.
- **No in-workspace image switching.** The image *is* the workspace;
  switching it requires recreation. Image selection is a launch-time concern
  only.

## Core principle: extensions are immutable published artifacts

An extension is a named, published entry in the catalog (`ffmpeg`,
`python313`). Once published, **its build-relevant fields (`type`, `value`,
`supported_bases`) do not change.** The only mutations are:

- **Retire** (soft-delete; gated at launch and selection).
- **Publish a new extension** with a different ID when a genuinely different
  build input is wanted (`python313` vs `python312`). (Per ruling #29
  below, apt-track packages do NOT version this way — the base is the
  version axis for them; version-suffixed IDs are the mise/`file`-type
  pattern.)

This mirrors how every package manager works — you don't change what
"python313" means; you version it as a new name. It also mirrors Talos, whose
extensions are upstream artifacts with real releases. (For apt-track
packages, ruling #29 below supersedes the version-as-new-name pattern —
the base is the version axis there.) Cosmetic metadata (a
human-readable description, sort order) may be edited freely.

This principle is load-bearing: because an extension ID is a stable
reference to a stable value, a selection of extension IDs is a stable
reference to a stable set of build inputs, which makes content-addressing
and the failure blocklist *simple* (see below). No frozen-snapshot
machinery is required to defend against edits, because there are no edits.

### Ruling (2026-08-17): the base IS the version axis for system packages

Evaluated and decided: extension versioning is **not** a factory
concern. For apt-track system packages (ffmpeg, libgl, …) the Debian
suite determines the version, so **selecting a version means selecting a
base** (`ffmpeg` on bookworm = 5.1; on trixie = 7.x). Consequences,
deliberate:

- Extension IDs are **per-base in meaning**: the same ID resolves to
  different bytes on different bases. Since the base name is in the hash
  preimage, identical selections on different bases are *different
  schematics* — intended, not a bug.
- No version metadata, no floating/pinned identities, no per-base
  resolution table, no version dropdowns. The catalog stays flat.
- Multi-version-same-tool needs (ffmpeg 6 AND 7 in one image) are
  explicitly **self-served outside the factory**: the runtime ships
  build tools and a persistent PVC; users compile/source-install the
  extra version themselves. The factory does not owe them a mechanism.
- Escape hatch if this ever proves too blunt (documented, NOT built):
  the existing `file` extension type can ship operator-authored static
  builds at versioned paths (`ffmpeg7-static`), which is
  base-independent and co-installable. Adding such entries later
  requires no model change.

This ruling supersedes any reading of this document that implies
per-extension version selection. The base-update pill (#928) remains
the sanctioned migration path: re-save on the new base → new hash →
explicit, diff-previewed change.

## Design model: Talos image factory

Mirrors `factory.talos.dev`: a fixed set of operator-approved bases, a fixed
set of selectable extensions, a stable schematic identifier independent of
version, and version carried as a separate axis.

| Talos | LLMSafeSpaces |
|---|---|
| Fixed flavors | Operator-curated base catalog (name + version rows) |
| System extensions | Catalog extensions (apt/mise/file), immutable once published |
| Opaque schematic ID | `s-<sha256[:16]>` over (sorted selection IDs + base name) |
| `/<schematic>/<version>/<platform>` URL | `s-<hash>-<baseVersion>` image tag |
| Schematic decode via ID lookup | API endpoint reads the config's stored resolved values |

### The version/hash reconciliation

Two axes, deliberately separated:

- **Hash** — content-addresses the selection + base *name*. Computed at
  config-save time. Stable across base *versions* (Talos model: `s-{ffmpeg}`
  is the same hash whether bookworm is at 0.6.0 or 0.6.1). Stable forever,
  because extensions are immutable — the IDs in the selection reference
  invariant values.
- **Base version** — a separate axis. A config pins `(hash, base_name,
  base_version)`. The image tag is `<hash>-<baseVersion>`. A new base
  version for an existing hash is a new image, not a new hash.

```
hash       = s-<sha256[:16] over (sorted selection IDs + base name)>
image tag  = <hash>-<baseVersion>           e.g. s-9f2a3c1b-0.6.0
image ref  = ghcr.io/lenaxia/llmsafespaces/ws:<tag>
```

Because extensions are immutable, a given hash always resolves to the same
build inputs. Rebuilding the same hash+version is a no-op-equivalent push
(same content → same digest). Tags are effectively immutable in practice
without enforcement. The image *digest* (returned by the build) is the
true immutable anchor; workspaces pin digest where it matters.

### Decode

`GET /configs/{hash}` returns the stored resolved values (captured at save
time as a convenience for decode-after-retirement, and to avoid N catalog
lookups on read). This is **not** part of the hash preimage — it's a cached
projection. The hash is over IDs; the resolved values are stored alongside
for display. If an extension is later retired, the stored resolved values
still decode correctly (the config's meaning is preserved).

### Controller untouched — for real

The controller and `RuntimeEnvironment` CRD are genuinely untouched: no new
phase, no new condition, no API-writing-workspace-status. The image factory
runs entirely inside the API and only hands the workspace a final, ready
image ref after the build succeeds. With eager-on-save builds, a config can
only be *launched* once it is Ready, so the workspace never waits on a build
and never observes a build failure. The existing `Workspace.spec.image` /
`Pending` / `Creating` flow is reused unchanged.

## Components and ownership

The image factory is **not a standalone long-running service**. It is a
build verb (GitHub Actions), a config (the catalog), and a small set of
API endpoints. Build status is derived on read (lazy GH API check, cached),
so there is no background worker, no poller, and no restart reconciliation.
The existing llmsafespaces API owns all user-facing state.

| Concern | Owner |
|---|---|
| Catalog (immutable extensions, versioned bases, arch config) | PostgreSQL tables, seeded from `catalog.seed.yaml` at API boot |
| Known failures (the blocklist) | `image_factory_known_failures` table (one row per genuinely-failed combo) |
| Selection → hash | Pure function in the API (library) |
| Hash → selection (decode) | API endpoint; reads `image_factory_configs.resolved_values` |
| Friendly names, saved configs, org policy | llmsafespaces API + PostgreSQL |
| Build execution | GitHub Actions workflow (`workflow_dispatch`) |
| Build status | Derived on read via cached GH API check against `gh_run_id` |

### API surface (added to the existing llmsafespaces API)

```
GET  /v1/image-factory/catalog           extensions, versioned bases, arch config, known-failures (for greying out)
POST /v1/image-factory/configs           save selection + friendly name → resolves, computes hash, fires build
GET  /v1/image-factory/configs           my configs + org configs + platform configs (with derived status pills)
GET  /v1/image-factory/configs/{hash}    decode: resolved values, derived build status, image ref
GET  /v1/image-factory/builds/{id}       single build detail (derived status from GH; explanation if rejected)
```

There is no `POST /builds` endpoint visible to users — builds fire implicitly
on config save (when the resolved selection has no existing successful
build). Build-status endpoints are read-only and derive live state from GH.

## Catalog

The catalog is the closed universe of what a schematic can select. It is
operator/platform-owner curated. Users request new entries via the project
issue tracker (same model as requesting a new Talos flavor).

### Storage: PostgreSQL, seeded from YAML at boot

A `catalog.seed.yaml` ships in the repo and is **idempotently upserted at
API boot** into the catalog tables — mirroring the existing Tier 1
instance-settings pattern (`pkg/settings/instance_service.go`). Git history
records deliberate operator edits to the seed; runtime mutation (retiring
an extension, publishing a base version, an admin un-flagging a false
positive via the portal) hits the DB without a deploy. Seed entries that a
runtime admin has since modified are not overwritten on the next boot (seed
wins on insert, runtime wins on update — same semantics as
`SetHelmOverrides`).

**Tables:**

```sql
-- Platform-level factory config. Single row (enforced by CHECK).
-- Platform owner owns this because they control what compute the cluster
-- offers; no point building for an arch with no nodes to run it.
CREATE TABLE image_factory_platform_config (
    id              INTEGER PRIMARY KEY DEFAULT 1 CHECK (id = 1),
    architectures   TEXT[] NOT NULL DEFAULT '{linux/amd64}',
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Approved bases. Composite key (name, version): old versions persist so
-- existing configs keep working after a bump. Bases genuinely version over
-- time (Debian releases, base image rebuilds), so they ARE append-only by
-- version — unlike extensions.
CREATE TABLE image_factory_bases (
    name        TEXT NOT NULL,
    version     TEXT NOT NULL,
    image       TEXT NOT NULL,
    tag         TEXT,
    digest      TEXT,                            -- wins over tag when set
    is_default  BOOLEAN NOT NULL DEFAULT FALSE,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (name, version)
);

-- Selectable extensions. IMMUTABLE once published: build-relevant fields
-- (type, value, file_spec, supported_bases) do not change after creation.
-- The only mutation is `retired` (soft-delete). To change a build input,
-- publish a new extension with a new ID and retire the old one.
-- Rationale: see "Core principle" above. This is what makes content-
-- addressing and the failure blocklist simple.
CREATE TABLE image_factory_extensions (
    id              TEXT PRIMARY KEY,            -- "ffmpeg", "python313"
    type            TEXT NOT NULL,               -- "apt" | "mise" | "file"
    value           TEXT NOT NULL,
    file_spec       JSONB,                       -- {path, mode} when type=file
    supported_bases TEXT[] NOT NULL,             -- base *names* this is valid on
    retired         BOOLEAN NOT NULL DEFAULT FALSE,
    review_requested BOOLEAN NOT NULL DEFAULT FALSE,  -- LLM flagged; admin reviews
    description     TEXT,                        -- cosmetic; the only freely-editable field
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT ext_type CHECK (type IN ('apt','mise','file'))
);

-- Known-failure blocklist. One row per genuinely-failed combination
-- (written only after a real failure — see "Failure handling"). This IS
-- the blocklist: a query over this table decides whether a selection is
-- greyed out / rebuildable. Simpler than a separate failure-counting
-- structure because failures are rare (~1% of builds).
CREATE TABLE image_factory_known_failures (
    selection_hash TEXT NOT NULL,                -- hash of (sorted selection IDs + base name)
    selection      TEXT[] NOT NULL,              -- the sorted IDs, for display
    base_name      TEXT NOT NULL,                -- base name (blocks across all versions)
    explanation    TEXT,                         -- LLM-generated reason
    failure_reason TEXT,                         -- raw log tail, for admin review
    detected_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    retriable      BOOLEAN NOT NULL DEFAULT TRUE,-- admin can set false to permanently block
    PRIMARY KEY (selection_hash, base_name)
);

-- Saved configs. resolved_values is a cached projection of the immutable
-- extension values at save time — stored for convenient decode and to
-- survive extension retirement. NOT part of the hash preimage.
--
-- resolved_values shape:
--   { "<extension_id>": {"type": "apt"|"mise"|"file",
--                        "value": "<apt pkg | tool@ver | file body>",
--                        "file_spec": {"path": "/abs/path", "mode": "0644"}?} }
CREATE TABLE image_factory_configs (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    hash            TEXT NOT NULL,               -- s-<sha256[:16]> over (selection IDs + base name)
    name            TEXT NOT NULL,               -- friendly name
    selection       TEXT[] NOT NULL,             -- sorted extension IDs
    resolved_values JSONB NOT NULL,              -- cached projection of immutable values (see shape above)
    base_name       TEXT NOT NULL,
    base_version    TEXT NOT NULL,
    scope           TEXT NOT NULL,               -- "member" | "org" | "platform"
    owner_id        UUID,                        -- member_id for member scope; NULL for platform
    org_id          UUID,                        -- org_id for org scope; NULL otherwise
    status          TEXT NOT NULL DEFAULT 'building',  -- "building" | "ready" | "rejected"
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT cfg_scope CHECK (scope IN ('member','org','platform')),
    CONSTRAINT cfg_status CHECK (status IN ('building','ready','rejected'))
);

-- Friendly-name uniqueness is scoped. Composite UNIQUE fails for platform
-- scope (both owner_id and org_id are NULL; NULLs are distinct in PG
-- uniqueness). Use partial indexes per scope.
CREATE UNIQUE INDEX cfg_name_member   ON image_factory_configs (owner_id, name) WHERE scope = 'member';
CREATE UNIQUE INDEX cfg_name_org      ON image_factory_configs (org_id, name)    WHERE scope = 'org';
CREATE UNIQUE INDEX cfg_name_platform ON image_factory_configs (name)            WHERE scope = 'platform';

-- Build attempts. One row per API dispatch. Transient retry happens
-- INSIDE the GH Actions workflow (decision: retry is a workflow concern,
-- not an API concern), so the API sees exactly one dispatch + one final
-- result. Keeps the API stateless — no in-API retry scheduling, no
-- background worker.
CREATE TABLE image_factory_builds (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    config_id       UUID NOT NULL REFERENCES image_factory_configs(id),
    hash            TEXT NOT NULL,
    base_name       TEXT NOT NULL,
    base_version    TEXT NOT NULL,
    resolved_values JSONB NOT NULL,              -- copied from config (immutable record of inputs)
    architectures   TEXT[] NOT NULL,             -- copied from platform_config (immutable record)
    image_ref       TEXT,                        -- set on success
    digest          TEXT,                        -- set on success
    status          TEXT NOT NULL,               -- "dispatched" | "succeeded" | "failed"
    gh_run_id       BIGINT,                      -- GitHub Actions run id
    callback_token  TEXT,                        -- per-build random secret; workflow POSTs it back (decision #18)
    failure_reason  TEXT,                        -- raw log tail on failure
    explanation     TEXT,                        -- LLM-generated, set on failure (may be null if LLM down — see Degradation)
    triggered_by    UUID,                        -- member_id; NULL for platform/system-initiated
    started_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    finished_at     TIMESTAMPTZ,
    CONSTRAINT build_status CHECK (status IN ('dispatched','succeeded','failed'))
);

-- Coalescing index: a save with an existing in-flight or successful build
-- for (hash, base_version) links instead of dispatching a duplicate.
CREATE INDEX idx_builds_config ON image_factory_builds (config_id);
CREATE INDEX idx_builds_dedupe ON image_factory_builds (hash, base_version, status);
CREATE INDEX idx_builds_gh_run ON image_factory_builds (gh_run_id) WHERE gh_run_id IS NOT NULL;
```

The effective selectable set for an `(extension, base_name)` pair is
`supported_bases ∋ base_name AND NOT retired`. A *combination* known-failure
is looked up in `image_factory_known_failures` by `(selection_hash,
base_name)` where `retriable = true OR retriable = false` (the UI greys out
non-retriable ones permanently; retriable ones show "known to fail, will
retry on save").

**Seed file** (`catalog.seed.yaml`, in the repo):

```yaml
# Platform owner configures which architectures the factory builds for.
# This is the compute the platform actually offers.
architectures: [linux/amd64, linux/arm64]

bases:
  - name: bookworm
    version: "0.6.0"
    image: ghcr.io/lenaxia/llmsafespaces/base
    tag: "0.6.0"
    isDefault: true
  - name: trixie
    version: "0.1.0"
    image: ghcr.io/lenaxia/llmsafespaces/base-trixie
    digest: "sha256:..."

extensions:
  - id: ffmpeg
    type: apt
    value: ffmpeg
    supportedBases: [bookworm, trixie]
    description: "FFmpeg multimedia framework"
  - id: libgl1
    type: apt
    value: libgl1
    supportedBases: [bookworm]
  - id: python313
    type: mise
    value: python@3.13
    supportedBases: [bookworm, trixie]
  - id: motd-welcome
    type: file
    value: { path: /etc/motd, content: "welcome\n" }
    supportedBases: [bookworm, trixie]
```

No `run` type, no `env` type — those were the injection vectors. Apt
packages are constrained to valid apt names; mise entries to `tool@version`;
files to a fixed set the operator publishes (contents are operator-authored,
not user-authored). A user only ever *selects IDs*.

## Failure handling: transient retry inside the workflow

Apt builds from official Debian repos succeed ~99% of the time. The failure
path is therefore intentionally lightweight — disproportionate machinery
here is the wrong level of abstraction for a rare event.

**Retry policy: retry lives inside the GH Actions workflow.** The workflow
has a `retry-on-transient` step that re-runs the build once if attempt 1
fails with a transient-looking error (keyword match on the log tail:
"timeout", "502", "503", "temporary failure", "Could not resolve host"). If
attempt 1 fails with a clearly non-transient error (apt package not found,
file path invalid), no retry. From the API's perspective there is **one
dispatch, one final result** — transient classification is a workflow
concern, not an API concern. This keeps the API stateless (no `attempt`
column, no in-API retry scheduling, no background worker).

Conservative: when uncertain, the workflow retries (a wasted retry is
cheaper than a false "real failure" that blocklists a working combo).

### What "prevented in the future" means

The `image_factory_known_failures` table *is* the blocklist. When any user
subsequently saves a config whose `(selection_hash, base_name)` matches a
known-failure row:

- If `retriable=true`: the save still fires a build (it's a retry attempt —
  maybe the base has bumped or the apt mirror recovered). The UI warns
  "this combination has failed before; retrying."
- If `retriable=false`: the save is rejected at submit time with "this
  combination is known not to build: <explanation>." No build is fired.
  The UI greys it out.

### Recovery / un-block

- **Admin un-block** (sets `retriable=true`, or deletes the known-failure
  row): this **triggers a rebuild of all `rejected` configs** matching that
  `(selection_hash, base_name)`. The admin action is "I believe this is
  fixed (base bumped, mirror recovered); retry everything affected." This
  is explicit and fixes the stuck-Rejected failure mode — un-block is not
  passive.
- **User edits and re-saves** with a different selection → new hash → not
  in known-failures → fresh build. (Note: because extensions are immutable,
  the user can't "edit the apt value" — but they can pick a different
  extension, drop one, or switch base.)

There is deliberately **no user-facing retry button**. Users are never
concerned with retrying. Recovery is admin-initiated (un-block → rebuild) or
user-initiated (different selection → different hash).

## Build trigger: eager on save, selection-change-gated

Saving a config resolves the selection, computes the hash, and — if no
existing successful build matches `(hash, base_version)` — fires a build
immediately. The config goes straight to `building` in the selector.

**Coalescing (load-bearing for cost).** Before dispatching, check for an
existing in-flight (`status='dispatched'`) or successful (`status='succeeded'`)
build for the same `(hash, base_version)`. If found, **link, don't
dispatch** — the new config points at the existing build row; no new GH
Actions run fires. Without this, N users saving the same popular combo (e.g.
ffmpeg+node) burn N× identical multi-arch builds for one image. This is the
single biggest cost guard in the system.

**Dispatch-vs-commit ordering (load-bearing for liveness).** `POST /configs`
dispatches the workflow **before** committing the config row. If dispatch
succeeds, the row is committed with `status='building'` and the `gh_run_id`.
If dispatch fails (GH down, rate-limited), the row is **not** committed —
the API returns an error and the user retries. This guarantees no config is
ever stranded at `building` with a null `gh_run_id` and no recovery path.

**A save does NOT fire a build when:**

- The friendly name was the only change (re-save identical selection).
- `(hash, base_version)` already has a successful build (config → `ready`).
- An in-flight build exists (config links to it; `building`).
- `(selection_hash, base_name)` is in `known_failures` with
  `retriable=false` (submit-time rejection; config never created).

**A save DOES fire a build when:**

- `(hash, base_version)` is novel and not permanently blocked.
- `(selection_hash, base_name)` is in `known_failures` with
  `retriable=true` (retry attempt after admin un-block or a brave user).

Eager-on-save is load-bearing: it means a config can only be launched once
Ready, which keeps the controller genuinely untouched. The cost is that
every saved *novel* config fires a real build, including configs never
launched. This is accepted — public-repo GH Actions budgets are generous;
rate limits are deferred (open items).

## Build dispatch contract

The workflow dispatch and its callback are the trust boundary between the
API and GitHub Actions. Specified exactly:

**Dispatch inputs** (passed to `workflow_dispatch`):

```yaml
build_id: <uuid>           # the image_factory_builds.id
callback_url: <url>        # API endpoint that records the result
callback_token: <secret>   # per-build random secret (32 bytes, hex)
hash: <s-...>              # for the image tag
base_name: <name>
base_version: <version>
base_image_ref: <ref>      # base.image + @digest or :tag, resolved by API
architectures: [linux/amd64, ...]
resolved_values: <json>    # the build inputs (see shape in schema)
```

**Callback authentication.** The API generates a `callback_token`
(crypto/rand, 32 bytes hex) at dispatch time, stores it on the build row,
and passes it as a workflow input. The workflow's final step POSTs the
result to `callback_url` with `Authorization: Bearer <callback_token>`. The
API compares with `subtle.ConstantTimeCompare`. Without a match the POST is
403'd and ignored. This is the only path by which an external runner can
mutate build state, and it is scoped to exactly one build.

**Callback payload** (POST body, JSON):

```jsonc
{
  "status": "succeeded" | "failed",
  "digest": "sha256:...",          // only on success
  "failure_reason": "<log tail>"   // only on failure
}
```

On success: build → `succeeded`, config → `ready`, image_ref/digest set.
On failure: build → `failed`, config → `rejected`; the API invokes the
LLM explanation seam and writes the `known_failures` row.

**On-read derivation is still the source of truth** (decision #18): if the
callback is lost (API down, network), the next `GET /configs` or
`GET /builds/{id}` that reads the in-flight build queries the GH Actions
API for `gh_run_id`, observes completion, and applies the same transition.
The callback just makes the common case immediate.

## Build execution: GitHub Actions

A workflow (`.github/workflows/image-build.yml`) triggered by
`workflow_dispatch`, parameterized by the resolved values + base version.
It:

1. Renders a deterministic Dockerfile from the resolved values + base
   version (pure function — identical inputs render an identical Dockerfile).
2. Builds multi-arch via `docker buildx`, for the architectures in
   `image_factory_platform_config.architectures` (platform owner controls
   this — they control what compute exists).
3. Pushes to ghcr.io.
4. On success: the workflow's final step records the digest (see "status
   derivation" below). Config → `ready`.
5. On failure: the workflow's final step records the failure reason; the
   API applies the retry/real-failure policy.

Builds are replaceable and stateless — re-triggering produces the same
image. The GitHub-hosted runner is ephemeral; builder isolation is
inherited from GitHub Actions.

### Build status: derived on read, not background-polled

There is **no background worker, no poller, no restart reconciliation.**
Build status is derived lazily on read:

- `GET /configs` and `GET /builds/{id}` check in-flight builds (status
  `building`) by querying the GH Actions API for the `gh_run_id`, with a
  per-run result cached for ~30s in the API process.
- When the GH run is observed complete, the API transitions the build row
  to `succeeded`/`failed` and the config to `ready`/`rejected`, applying
  the retry policy on failure.
- The GH Action's final step also POSTs the result to a callback endpoint
  on the API (best-effort; the on-read derivation is the source of truth,
  so a missed callback just means the status updates on next read rather
  than immediately).

This means: if a build finishes while no one is looking, its status updates
on the next read of any config or build detail. Acceptable — there is no
user waiting on it (the user who saved it will look eventually; the
selector pill updates then). If the API is down when the GH Action
finishes, the callback is lost but the on-read derivation recovers it.

This is what makes "no standalone service" trivially true: there is no
process whose job is to watch builds. The API is request-driven end to end.

## Failure-handling seam: platform-LLM explanation

Invoked **once**, on the real (attempt-2 or non-transient-attempt-1)
failure:

1. The GH Action failure step captures the log tail.
2. The API calls the platform's existing LLM infrastructure (LiteLLM/vLLM
   in-cluster) for a summary + suggested next action.
3. The summary is stored on the build record and on the `known_failures`
   row; the config flips to `rejected`; the user is notified with the
   explained rejection.
4. Optional: an "investigate in a workspace" button spins up a workspace on
   the default base image pre-loaded with the build context + error log —
   dogfooding the platform for hard cases. Note: the investigation
   workspace runs the *plain base* (no extensions), since the extended
   image failed to build.

**Attribution:** the LLM is asked whether a single extension is at fault
(e.g. a typo'd apt package — though extensions are operator-authored, typos
still happen). If it attributes confidently, the extension is flagged for
admin review (a `review_requested` flag, not auto-retire). Otherwise the
failure is a combination conflict → known-failure row. Conservative
default: when uncertain, record as combination failure with `retriable=true`
(over-block is recoverable; under-block re-surfaces the failure).

The LLM never sees secrets (there are none in resolved values or build
context).

**Degradation when LLM is down.** If the LLM call fails or times out, the
config still flips to `rejected` and the `known_failures` row is still
written, but with a fallback explanation ("build failed; details
unavailable, contact admin") and `explanation` left null on the build row.
A lazy retry: the next time an admin views the known-failure in the portal,
if `explanation` is still null, the API retries the LLM call. No
user-visible change until then — the user sees the fallback string. This
avoids a hard dependency on LLM availability for the failure path to
function.

## Retirement vs launch

Retirement blocks **new config creation and new builds**, not launching an
already-Ready config. A Ready config's image exists in the registry; if a
user built it before the extension was retired, it still launches. This is
the least-surprising behavior: the user built it, it works, they can use
it. What they *cannot* do is create a new config selecting the retired
extension, or trigger a rebuild of a config whose selection includes it
(which would fail the launch-time validation anyway). Retirement is
one-directional deprecation, not retroactive revocation.

## Admin portal

Operator/admin surface for managing the catalog and observing builds.
Distinct from the consumer UX (settings + launch picker). Backed by
admin-only API endpoints over the catalog tables.

**Endpoints (admin-scoped):**

```
GET    /v1/admin/image-factory/platform-config   current architectures
PUT    /v1/admin/image-factory/platform-config   set architectures (platform owner controls compute)

GET    /v1/admin/image-factory/bases             list bases (all versions)
POST   /v1/admin/image-factory/bases             add a base version
PUT    /v1/admin/image-factory/bases/{name}/{version}   edit / mark default
DELETE /v1/admin/image-factory/bases/{name}/{version}   retire a version

GET    /v1/admin/image-factory/extensions        list extensions
POST   /v1/admin/image-factory/extensions        publish a new extension (immutable after this)
PUT    /v1/admin/image-factory/extensions/{id}   edit description only (cosmetic); build fields rejected
DELETE /v1/admin/image-factory/extensions/{id}   retire (sets retired=true)

GET    /v1/admin/image-factory/known-failures    current blocklist, with explanations + retriable flag
PUT    /v1/admin/image-factory/known-failures/{key}   toggle retriable (true → rebuild affected configs; false → permanent block)
DELETE /v1/admin/image-factory/known-failures/{key}   clear the failure (rebuild affected configs)

GET    /v1/admin/image-factory/configs           platform-scoped published configs
POST   /v1/admin/image-factory/configs           publish a platform config — fires a build

GET    /v1/admin/image-factory/builds            build queue + history (status, attempts, who triggered, duration)
GET    /v1/admin/image-factory/builds/{id}       single build detail incl. failure reason + explanation

PUT    /v1/admin/orgs/{org}/image-factory/policy     set policy
GET    /v1/admin/orgs/{org}/image-factory/configs    org-scoped configs
POST   /v1/admin/orgs/{org}/image-factory/configs    org owner publishes a config — fires a build
```

**Authorization:**

| Endpoint group | Allowed |
|---|---|
| platform-config, bases, extensions, known-failures, platform configs, builds | platform owner only |
| orgs/{org}/... | org owner of that org, plus platform owner |

**Portal surfaces (web UI):**

1. **Catalog management** — publish/retire extensions and base versions.
   The seed file remains the reviewable baseline in git; the portal writes
   the DB for fast iteration; permanent changes are back-ported into
   `catalog.seed.yaml` via PR. Note: an extension's build fields are
   immutable after publish — to change a build input, publish a new
   extension ID and retire the old.
2. **Known-failures review** — see failed combos with their LLM
   explanations and raw log tails; toggle `retriable` (true → all affected
   `rejected` configs rebuild; false → permanent grey-out) or clear a
   failure entirely.
3. **Platform configs** — publish platform-wide named configs.
4. **Org policy + configs** — org-owner view: set
   `assemble`/`published_only`, publish org configs.
5. **Build observability** — queue, history, per-build status and attempt
   count; on failure the raw reason + LLM explanation; aggregate build
   counts/durations.

## Authorization model

Three actor levels: **platform owner**, **org owner**, **org member**,
**solo member** (a member with no org).

| Actor | Can request custom images | Policy source |
|---|---|---|
| Platform owner | yes, always | self |
| Solo member | yes, always | none — solo |
| Org owner | yes, always | self; sets policy for members |
| Org member | yes **iff** org policy allows | org owner |

Org-owner policy is binary:

- **`assemble`** — members may assemble their own selection from the
  catalog (subject to known-failures).
- **`published_only`** — members may only launch from configs the org
  owner has published. The member can still *see* the catalog (to request
  additions), but the launch picker shows only org-published +
  platform-published configs.

## Friendly names

Three scopes, resolved in this order at render time (first match wins):

1. **Member-scoped** — a name a user gave to a hash.
2. **Org-scoped** — a name an org owner published for their org's members.
3. **Platform-scoped** — platform-wide names for canonical configs.

Collisions resolve to the narrowest scope (member beats org beats
platform). Names are scoped, not global — two orgs can both publish
"ml-stack."

## Config lifecycle states

Configs (not workspaces) carry a status shown as a pill in the launch
picker:

| State | Meaning | Trigger |
|---|---|---|
| **Building** | Build in flight (attempt 1 or 2) | Config saved with a novel selection; or admin un-block triggered a rebuild |
| **Ready** | Image exists in the registry; launchable | Build succeeded |
| **Rejected** | Build failed for real; combo in known-failures | Attempt 2 (or non-transient attempt 1) failed |

**Workspaces have no build/failed state.** A config can only be launched
once Ready — the launch UI greys out Building and Rejected configs. This
keeps the controller untouched.

No user-facing retry. Recovery from Rejected is admin un-block (→ rebuild)
or user picks a different selection (→ different hash). No `stale` state:
existing Ready configs stay on their pinned base version; a new base
version is a new image, built only when a config targets it.

No GC in v1.

## Settings → UX

**Settings page ("Workspace Images"):**

1. User browses the catalog (extensions + versioned bases), read via
   `GET /v1/image-factory/catalog`.
2. Assembles a selection by checkbox/dropdown. Known-failed combos render
   greyed ("known not to build") or warned ("failed before, retrying")
   based on the `retriable` flag.
3. Names it ("ml-stack"), saves → resolves, computes hash, stores
   `(owner, name, selection, resolved_values, hash)`, fires a build.
   Config immediately shows as Building.
4. The config transitions Building → Ready (or → Rejected with the LLM
   explanation) asynchronously; the selector pill updates via existing SSE
   event infra on next read.

**Launch dialog:**

1. Image picker shows my configs + org configs + platform configs, each by
   friendly name.
2. Policy gate: `published_only` members see only org-published +
   platform configs.
3. Each config shows a status pill: **Building** (greyed, not launchable),
   **Ready** (launchable), **Rejected** (greyed, with explanation +
   "investigate in a workspace" button).
4. User picks a Ready config and launches. Workspace starts against an
   already-built image — no build wait at launch.

UX cost accepted: a novel config is not launchable for ~10 minutes after
save. Users see Building up-front in the selector; they are never blocked
*at launch*.

## Open items (deferred, not blocking)

- **Rate limits / quotas** — intentionally not in v1 (public-repo GH budget
  is generous). Revisit if measured: per-user novel-build limits, org
  quotas, debounce windows.
- **Base-update pill** (a.k.a. "update available" affordance) — the
  sanctioned migration path per ruling #29; v1 shipped without it,
  tracked in #928.
- **Registry GC** — no retention policy in v1.
- **Org-owner quota on published configs** — whether an org can publish
  unboundedly.
- **Catalog contribution path** — community-contributed extensions via PR
  (currently operator-only).
- **Build timeout** — a hung GH run leaves a build at `building`. Need a
  max-duration after which the attempt is treated as failed (counts as the
  transient retry). Exact duration TBD in the build-workflow story.
- **Secret scanning on `type: file`** — run gitleaks/trivy on the rendered
  build context in CI. Wire into the build-workflow story.
- **`RuntimeEnvironment` creation policy** — does launching a factory
  config auto-create a `RuntimeEnvironment` CR per config, or reference the
  image ref directly? Resolve in the controller-integration story.
- **SSE keepalive** — builds take ~10 min; long-lived SSE through proxies
  may need keepalive pings or a polling fallback.
- **Base-version integrity** — `configs.base_version` should FK to
  `bases(name, version)` or be launch-time-checked, so a config can't pin
  a deleted base version. Resolve in the storage story.

## Decisions summary

| # | Decision | Rationale |
|---|---|---|
| 1 | Opaque SHA hash, decode via API lookup | Talos model; no in-band/secrecy issues |
| 2 | Hash over (selection IDs + base name); base version is a separate axis | Version-stable; content-stable via extension immutability |
| 3 | Image tag = `s-<hash>-<baseVersion>`; CRD points at full ref | No CRD indirection; version explicit |
| 4 | No standalone factory service — API + GH Actions, status derived on read | No runtime state, no background worker, trivially stateless |
| 5 | Selection-only input (no free text, no `run`, no `env`) | Eliminates injection surface |
| 6 | No secrets in images/hash | Stays in K8s-Secret injection path |
| 7 | **Extensions are immutable-once-published; only retire or publish-new** | Makes content-addressing + blocklist simple by construction; matches how package managers work |
| 8 | Bases are append-only by `(name, version)` | Bases genuinely version over time; old versions persist for existing configs |
| 9 | Catalog in PostgreSQL, seeded from `catalog.seed.yaml` at boot | Runtime mutation (retire, un-block) needs DB; seed keeps git review |
| 10 | `resolved_values` cached on config for decode; not in hash preimage | Survives extension retirement; avoids N lookups on read |
| 11 | Open catalog + `known_failures` table as the blocklist | Failures rare (~1%); one table is the right level |
| 12 | Transient retry inside the GH Actions workflow, not the API | API stays stateless; one dispatch + one final result; no `attempt` column |
| 13 | Known-failure `retriable` flag; admin toggle rebuilds affected configs | Simple recovery; fixes stuck-Rejected by making un-block active |
| 14 | No user-facing retry | Users never concerned with retrying; different selection → different hash |
| 15 | Build trigger eager on save, selection-change-gated | Configs only launchable when Ready → controller untouched |
| 16 | **Build coalescing: link, don't dispatch, on duplicate (hash, base_version)** | Prevents N× identical builds for a popular combo; the biggest cost guard |
| 17 | **Dispatch-before-commit: rollback row on dispatch failure** | No config stranded at `building` with null `gh_run_id`; no restart reconciliation needed |
| 18 | **Per-build `callback_token`; workflow POSTs it back; ConstantTimeCompare** | Only external runners can mutate build state; scoped to exactly one build |
| 19 | Controller genuinely untouched — no new phase/condition | API owns image lifecycle; workspace only sees ready image ref |
| 20 | Config states: Building / Ready / Rejected; workspaces have no build/failed state | Failures surface on configs, never on workspaces |
| 21 | Build status derived on read (cached GH API check) + best-effort authenticated callback | No poller, no restart reconciliation; on-read is source of truth |
| 22 | Failure explanation via platform LLM, once; null on LLM-down with fallback string + lazy retry on admin view | No hard dependency on LLM availability for the failure path |
| 23 | Retirement blocks new configs/builds, not launching already-Ready configs | Image exists; least-surprising behavior; one-directional deprecation |
| 24 | Org policy: `assemble` or `published_only` | Full policy space given dropdown-only input |
| 25 | Friendly names: member > org > platform scope; partial unique indexes per scope | No global namespace; NULLs in PG uniqueness handled |
| 26 | Platform owner configures build architectures | Controls what compute is available |
| 27 | GitHub Actions builds, ghcr.io storage | Free hosting, replaceable, ephemeral runners |
| 28 | No GC, no rate limits in v1 | Generous public-repo budget; revisit when measured |
| 29 | **(2026-08-17) The base is the version axis for apt-track system packages; no per-extension versioning, no multi-version support** | Debian suites fix package versions, so version selection IS base selection; multi-version needs self-serve via build tools; static-build `file` extensions remain the documented escape hatch |
