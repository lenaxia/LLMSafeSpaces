# Image Factory — custom workspace images

**Author:** design session 2026-08-01 (revised 2026-08-02)
**Status:** Approved (design — no implementation yet)
**Related:** `pkg/apis/llmsafespaces/v1/runtimeenvironment_types.go`, `design/archive/v1/0007_2025-03-05_runtimeenv.md` (legacy multi-image model, superseded), Epic 7 (runtime interception — closed, incompatible)

## Problem

Workspaces run a single blessed base image (`runtimes/base`, Debian
bookworm). Users and agents occasionally need dependencies the provided
package managers (`mise`/`pip`/`npm`/`go`) **cannot** supply — system
libraries (libgl, libssl, CUDA, ODBC), vendored binaries, proprietary CLIs,
or one-off system setup. Today there is no path for a user to get those into
their workspace image. The motivating symptom was a binary that failed to
start with a missing libc; that is one instance of the general gap.

We need a way for users (within authorization) to obtain workspace images
that extend an operator-approved base with extra dependencies — without
exposing a free-text injection surface, without storing secrets in images,
and without requiring platform operators to hand-build a new image per
request.

## Non-goals

- **No secrets in images or schematic hashes.** Credentials stay in the
  existing injection path (K8s Secrets, never baked into image layers). This
  is non-negotiable and shapes several decisions below.
- **No free-text user input into the build.** Schematics are a *selection*
  of catalog item IDs, never arbitrary commands/files. This eliminates the
  injection / arbitrary-code-execution-on-builders attack surface entirely.
- **No in-workspace image switching.** The image *is* the workspace;
  switching it requires recreation. Image selection is a launch-time concern
  only.

## Design model: Talos image factory

Mirrors `factory.talos.dev`: a fixed set of operator-approved bases, a fixed
set of selectable extensions, a stable schematic identifier that is
independent of version, and version carried as a separate axis.

| Talos | LLMSafeSpaces |
|---|---|
| Fixed flavors | Operator-curated base catalog (name + version rows) |
| System extensions | Catalog extensions (apt/mise/file) |
| Opaque schematic ID | `s-<sha256[:16]>` over the resolved-value snapshot |
| `/<schematic>/<version>/<platform>` URL | `s-<hash>-<baseVersion>` image tag |
| Schematic decode via ID lookup | API endpoint reads the frozen snapshot |

### The version/hash reconciliation (load-bearing)

Two axes, deliberately separated:

- **Hash** — content-addresses the resolved *extension values* + the base
  *name*. Computed at config-save time over a frozen snapshot of the
  extension values then-current in the catalog. This is stable across base
  *versions* (Talos model: `s-{ffmpeg}` is the same hash whether bookworm is
  at 0.6.0 or 0.6.1).
- **Base version** — a separate, parallel axis. A config pins `(hash,
  base_name, base_version)`. The image tag is `<hash>-<baseVersion>`. A new
  base version for an existing hash is a new image, not a new hash.

```
snapshot   = canonical JSON of {resolved extension values..., baseName}
hash       = s-<sha256[:16] over snapshot>
image tag  = <hash>-<baseVersion>           e.g. s-9f2a3c1b-0.6.0
image ref  = ghcr.io/lenaxia/llmsafespaces/ws:<tag>
```

### Why snapshot-and-hash (not append-only, not raw IDs)

An earlier draft hashed over *extension IDs* only. That broke when an admin
edited an extension's `value` in place: the ID was unchanged so the hash was
unchanged, but two materially different images would share one hash.
Content-addressing requires the preimage to cover the *resolved values*.

Two fixes were considered:

1. **Append-only extensions** (new version per edit). Rejected: version
   explosion on cosmetic edits; compat matrix grows from `ext × base` to
   `ext × ext-version × base × base-version`; retirement of a version
   reintroduces the stale state we wanted to avoid.
2. **Snapshot resolved values into the config at save time; hash over the
   snapshot.** Chosen. An admin edit legitimately changes the hash for
   *new* configs (content changed) while already-built images keep their old
   hash (their snapshot is frozen in the config row). Decode returns the
   stored snapshot, never a re-resolution, so it is exact forever.

Bases, by contrast, *are* append-only at the version level
(`image_factory_bases` key is `(name, version)`) — Debian releases genuinely
version over time, and old versions must persist so existing configs keep
working after a bump.

### Controller untouched — for real

The controller and `RuntimeEnvironment` CRD are genuinely untouched: no new
phase, no new condition, no API-writing-workspace-status. The image factory
runs **entirely inside the API** and only hands the workspace a final,
ready image ref after the build succeeds. With eager-on-save builds
(below), a config can only be *launched* once it is Ready, so the workspace
never waits on a build and never observes a build failure. The existing
`Workspace.spec.image` / `Pending` / `Creating` flow is reused unchanged.

## Components and ownership

The image factory is **not a standalone long-running service**. It is a
build verb (GitHub Actions), a config (the catalog), and a small set of API
endpoints. The existing llmsafespaces API owns all user-facing state.

| Concern | Owner |
|---|---|
| Catalog (extensions, versioned bases, compat matrix) | PostgreSQL tables, seeded from `catalog.seed.yaml` at API boot |
| Blocklist of bad combos | `image_factory_blocklist` (auto-grown after 3 failed attempts) |
| Selection → snapshot → hash | Pure function in the API (library) |
| Hash → selection (decode) | API endpoint; reads `image_factory_configs.snapshot` |
| Friendly names, saved configs, org policy | llmsafespaces API + PostgreSQL (`image_factory_configs`, org policy table) |
| Build execution | GitHub Actions workflow (`workflow_dispatch`) |
| Build status + retries | PostgreSQL `image_factory_builds`; API reconciles in-flight runs on restart |

A separate factory service is justified only if non-llmsafespaces consumers
need to build against the same catalog. That is not a current requirement.

### API surface (added to the existing llmsafespaces API)

```
GET  /v1/image-factory/catalog           extensions, versioned bases, blocklist (for greying out unsupported)
POST /v1/image-factory/configs           save selection + friendly name → resolves snapshot, computes hash, fires build
GET  /v1/image-factory/configs           my configs + org configs + platform configs (with status pills)
GET  /v1/image-factory/configs/{hash}    decode: frozen snapshot, build status, image ref
GET  /v1/image-factory/builds/{id}       status for the "Building" pill + SSE for notifications
```

Note: there is no `POST /builds` endpoint visible to users — builds fire
implicitly on config save (when the resolved selection has no existing
successful build record). The build-status endpoints are read-only.

The controller and `RuntimeEnvironment` CRD are **untouched**. The API
hands a finished image ref to the Workspace CRD exactly as today.

## Catalog

The catalog is the closed universe of what a schematic can select. It is
operator/platform-owner curated. Users request new entries via the project
issue tracker (same model as requesting a new Talos flavor).

### Storage: PostgreSQL, seeded from YAML at boot

The catalog lives in **PostgreSQL**, not a static YAML file — because the
blocklist must be runtime-mutable (auto-grown by build failures; see
compat-matrix policy). Splitting "supported extensions" (YAML) from
"blocked combos" (DB) would force every render to join a repo file with a
DB table. One runtime source of truth avoids that.

A `catalog.seed.yaml` ships in the repo and is **idempotently upserted at API
boot** into the catalog tables — mirroring the existing Tier 1
instance-settings pattern (`pkg/settings/instance_service.go`, where a
Helm/seed value is promoted on boot and runtime mutation writes the DB). Git
history records deliberate operator edits to the seed; runtime mutation
(auto-blocklist growth, an admin un-flagging a false positive via the
portal) hits the DB without a deploy. Seed entries that a runtime admin has
since modified are not overwritten on the next boot (seed wins on insert,
runtime wins on update — the same semantics as `SetHelmOverrides`).

**Tables:**

```sql
-- Approved bases. Composite key (name, version): old versions persist so
-- existing configs keep working after a bump. (name) is the Talos "flavor";
-- (name, version) is the buildable target.
CREATE TABLE image_factory_bases (
    name        TEXT NOT NULL,               -- "bookworm", "trixie"
    version     TEXT NOT NULL,               -- "0.6.0", "0.6.1"
    image       TEXT NOT NULL,
    tag         TEXT,
    digest      TEXT,                        -- wins over tag when set
    is_default  BOOLEAN NOT NULL DEFAULT FALSE,  -- default (name,version) for new configs
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (name, version)
);

-- Platform-level factory config. Single row (enforced by application logic).
-- The platform owner owns this because they control what compute the cluster
-- offers; there is no point building for an arch with no nodes to run it.
CREATE TABLE image_factory_platform_config (
    id              INTEGER PRIMARY KEY DEFAULT 1 CHECK (id = 1),
    architectures   TEXT[] NOT NULL DEFAULT '{linux/amd64}',  -- archs the factory builds for
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Selectable extensions. Mutable in place: edits legitimately change the
-- resolved value, so new configs get a new hash (the snapshot is taken at
-- save time). Existing configs are unaffected — their snapshot is frozen.
CREATE TABLE image_factory_extensions (
    id              TEXT PRIMARY KEY,        -- "ffmpeg", "python313"
    type            TEXT NOT NULL,           -- "apt" | "mise" | "file"
    value           TEXT NOT NULL,           -- apt pkg name | "tool@ver" | file body
    file_spec       JSONB,                   -- {path, mode} when type=file
    supported_bases TEXT[] NOT NULL,         -- base *names* this extension is valid on
    retired         BOOLEAN NOT NULL DEFAULT FALSE,  -- soft-delete; gated at launch
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT ext_type CHECK (type IN ('apt','mise','file'))
);

-- Auto-grown blocklist of combination failures. Only written after a combo
-- fails 3 times (see "Retry policy"). Per-extension faults are NOT stored
-- here — a single broken extension is retired via image_factory_extensions.
CREATE TABLE image_factory_blocklist (
    extension_set   TEXT[] NOT NULL,         -- sorted extension IDs from the snapshot
    base_name       TEXT NOT NULL,           -- base name (not version): blocks across all versions
    explanation     TEXT,                    -- LLM-generated reason (from the 3rd/final failure)
    last_failure_reason TEXT,                -- raw log tail from the final failure, for admin review
    first_failed_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    last_failed_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    failure_count   INTEGER NOT NULL DEFAULT 1,  -- increments on re-fail after an un-block
    unblocked_at    TIMESTAMPTZ,             -- set by admin to override; cleared if it re-fails 3x
    PRIMARY KEY (extension_set, base_name)
);

-- Saved configs. The snapshot column is what makes the hash exact forever:
-- it freezes the resolved values at save time. Decode reads it directly.
CREATE TABLE image_factory_configs (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    hash        TEXT NOT NULL,               -- s-<sha256[:16]> over snapshot
    name        TEXT NOT NULL,               -- friendly name
    selection   TEXT[] NOT NULL,             -- sorted extension IDs (the user's pick)
    snapshot    JSONB NOT NULL,              -- frozen resolved values (the hash preimage)
    base_name   TEXT NOT NULL,
    base_version TEXT NOT NULL,
    scope       TEXT NOT NULL,               -- "member" | "org" | "platform"
    owner_id    UUID,                        -- member_id for member scope
    org_id      UUID,                        -- org_id for org scope; NULL for platform/member
    status      TEXT NOT NULL DEFAULT 'building',  -- "building" | "ready" | "rejected"
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (scope, owner_id, org_id, name),  -- scoped uniqueness, see "Friendly names"
    CONSTRAINT cfg_scope CHECK (scope IN ('member','org','platform')),
    CONSTRAINT cfg_status CHECK (status IN ('building','ready','rejected'))
);

-- Build attempts. One row per attempt (up to 3 per combo before Rejected).
CREATE TABLE image_factory_builds (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    config_id       UUID NOT NULL REFERENCES image_factory_configs(id),
    hash            TEXT NOT NULL,
    base_name       TEXT NOT NULL,
    base_version    TEXT NOT NULL,
    snapshot        JSONB NOT NULL,          -- copied from config (immutable per build)
    image_ref       TEXT,                    -- set on success
    digest          TEXT,                    -- set on success
    status          TEXT NOT NULL,           -- "pending" | "building" | "succeeded" | "failed"
    attempt         INTEGER NOT NULL,        -- 1, 2, or 3
    gh_run_id       BIGINT,                  -- GitHub Actions run id (polling/webhook key)
    failure_reason  TEXT,                    -- raw log tail on failure
    explanation     TEXT,                    -- LLM-generated (set on the 3rd/final failure)
    triggered_by    UUID NOT NULL,           -- member_id who saved the config
    started_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    finished_at     TIMESTAMPTZ,
    CONSTRAINT build_status CHECK (status IN ('pending','building','succeeded','failed'))
);

CREATE INDEX idx_builds_config ON image_factory_builds (config_id, attempt);
```

The effective supported set for an `(extension, base_name)` pair is
`supported_bases ∋ base_name AND NOT retired`. A *combination* failure (a
set of extensions that breaks together even if each is individually fine)
is looked up in `image_factory_blocklist` where `unblocked_at IS NULL`.

**Seed file** (`catalog.seed.yaml`, in the repo):

```yaml
# Platform owner configures which architectures the factory builds for.
# This is the compute the platform actually offers — there is no point
# building for arm64 if no arm64 nodes exist in the cluster.
architectures: [linux/amd64, linux/arm64]

bases:
  - name: bookworm
    version: "0.6.0"
    image: ghcr.io/lenaxia/llmsafespaces/base
    tag: "0.6.0"
    isDefault: true
  - name: trixie
    version: "0.1.0"
    image: ghcr.io/lenaxia/llmsafespaces/base-trixie
    digest: "sha256:..."

extensions:
  - id: ffmpeg
    type: apt
    value: ffmpeg
    supportedBases: [bookworm, trixie]
  - id: libgl1
    type: apt
    value: libgl1
    supportedBases: [bookworm]
  - id: python313
    type: mise
    value: python@3.13
    supportedBases: [bookworm, trixie]
  - id: motd-welcome
    type: file
    value: { path: /etc/motd, content: "welcome\n" }
    supportedBases: [bookworm, trixie]
```

No `run` type, no `env` type in the initial design — those were the
injection vectors. Apt packages are constrained to valid apt names; mise
entries to `tool@version`; files to a fixed set the operator publishes
(contents are operator-authored, not user-authored). A user only ever
*selects IDs*.

### Compatibility matrix policy: open catalog, auto-growing blocklist (model b)

The catalog is open by default — any non-retired extension whose
`supported_bases` includes the chosen base name is selectable. There is
**no pre-verification** of every possible combination. Build failures drive
the blocklist (after retries — see below).

The system converges toward a closed allow-list over time, paid for by
real build failures rather than operator effort. First-time explained
failures are accepted as the cost of low maintenance.

### Retry policy: 3 attempts before Rejected

A build is retried up to **twice** (3 total attempts) before a config is
marked Rejected. This separates transient failures (runner flake, GH
outage, apt mirror hiccup) from genuinely bad combinations:

1. Attempt 1 fails → schedule attempt 2 (backoff). `image_factory_builds`
   row records the failure_reason; config stays `building`.
2. Attempt 2 fails → schedule attempt 3. Same.
3. Attempt 3 fails → this is a real failure:
   - The failure-seam (LLM) generates an explanation from attempt 3's log.
   - The `(extension_set, base_name)` is written to `image_factory_blocklist`
     with the explanation. Transient attempts 1–2 do **not** pollute the
     blocklist — only the 3rd/final failure writes it.
   - The config flips to `rejected` with the explanation surfaced in the
     selector.

The LLM explanation shown to the user is from the final (real) failure, not
the first transient one. `last_failure_reason` retains the raw log tail for
admin review.

## Admin portal

The operator/admin surface for managing the catalog and observing builds.
Distinct from the *consumer* UX (settings + launch picker). Backed by
admin-only API endpoints over the catalog tables.

**Endpoints (admin-scoped):**

```
GET    /v1/admin/image-factory/platform-config  current architectures list
PUT    /v1/admin/image-factory/platform-config  set architectures (platform owner controls what compute is built for)

GET    /v1/admin/image-factory/bases                 list bases (all versions)
POST   /v1/admin/image-factory/bases                 add a base version
PUT    /v1/admin/image-factory/bases/{name}/{version}  edit / mark default
DELETE /v1/admin/image-factory/bases/{name}/{version}  retire a version (blocks new configs; existing keep their pin)

GET    /v1/admin/image-factory/extensions            list extensions
POST   /v1/admin/image-factory/extensions            add an extension
PUT    /v1/admin/image-factory/extensions/{id}       edit value/supportedBases (changes hash for NEW configs; existing configs frozen)

POST   /v1/admin/orgs/{org}/image-factory/configs    org owner publishes a config for members — fires a build
```

**Authorization:**

| Endpoint group | Allowed |
|---|---|
| bases, extensions, blocklist review, platform configs, builds | platform owner only |
| orgs/{org}/... | org owner of that org, plus platform owner |

**Portal surfaces (web UI):**

1. **Catalog management** — add/edit/retire extensions and base versions.
   The seed file remains the reviewable baseline in git; the portal writes
   the DB for fast iteration, and changes intended to be permanent are
   back-ported into `catalog.seed.yaml` via PR (the portal is not a
   substitute for code review of the canonical set). Note: editing an
   extension's value does not affect existing configs (frozen snapshots) —
   only new configs created after the edit.
2. **Blocklist review** — see auto-blocklisted combos with their
   LLM-generated explanations, failure counts, and raw log tails; un-block
   a false positive (sets `unblocked_at`, which re-enables the combo until
   it re-fails 3x).
3. **Platform configs** — publish platform-wide named configs that every
   user sees at the platform scope of the friendly-name resolution.
4. **Org policy + configs** — the org-owner view: set
   `assemble`/`published_only`, publish org configs members can launch.
5. **Build observability** — build queue, history, per-build status and
   attempt count; on failure the raw reason + LLM explanation; aggregate
   view of build counts and durations against the shared GitHub Actions
   budget.

## Authorization model

Three actor levels: **platform owner**, **org owner**, **org member**,
**solo member** (a member with no org).

| Actor | Can request custom images | Policy source |
|---|---|---|
| Platform owner | yes, always | self |
| Solo member | yes, always | none — solo |
| Org owner | yes, always | self; sets policy for members |
| Org member | yes **iff** org policy allows | org owner |

Org-owner policy is binary:

- **`assemble`** — members may assemble their own selection from the
  catalog (subject to the blocklist).
- **`published_only`** — members may only launch from configs the org owner
  has published (named). The member can still *see* the catalog (so they
  can request additions), but the launch picker shows only org-published
  + platform-published configs.

This is the full policy space because input is dropdown-only: "any hash"
collapses to "any combo the catalog allows," so the only meaningful
restriction is whether the member may compose or only pick.

## Friendly names

Three scopes, resolved in this order at render time (first match wins):

1. **Member-scoped** — a name a user gave to a hash (the common case).
2. **Org-scoped** — a name an org owner published for their org's members.
3. **Platform-scoped** — platform-wide names for canonical configs.

Collisions across scopes resolve to the narrowest scope (member beats org
beats platform). Two orgs both publishing "ml-stack" is fine — names are
scoped, not global. A solo member and an org member can both have
"my-ml-stack" without conflict.

## Config lifecycle states

Configs (not workspaces) carry a status shown as a pill in the launch
picker:

| State | Meaning | Trigger |
|---|---|---|
| **Building** | Build in flight in GitHub Actions (within the 3-attempt budget) | Config saved with a novel selection; or a base version bump triggered a rebuild |
| **Ready** | Image exists in the registry; launchable | Build succeeded |
| **Rejected** | Build failed 3 times; combo is blocklisted | 3rd attempt failed; LLM explanation attached |

**Workspaces have no failed state and no build-wait state.** A config can
only be *launched* once it is Ready — the launch UI greys out Building and
Rejected configs. This is what keeps the controller genuinely untouched:
the workspace never waits on a build, because by the time the user can
launch it, the image already exists.

**No user-facing retry.** Users are never concerned with retrying. The
path from Rejected back to Ready is either: (a) edit the config and re-save
(a new selection → a new snapshot → a new hash → a new build), or (b) an
admin un-blocks the combo (clears `unblocked_at`; the config is eligible
for a fresh build on the next save that resolves to it). Retrying an
identical known-bad combo is deliberately not exposed — it would just burn
two more runs to re-fail.

No `stale` state for configs: when a base ships a new version, existing
Ready configs stay Ready on their pinned version. A new build for the new
version fires only if/when a config is re-saved against the new version
(or a new config is created against it). Old image tags persist (bases are
append-only by version).

No garbage collection in v1. Every distinct schematic produces a permanent
image. Revisit when registry storage becomes a measured problem.

## Build trigger

**Eager: build on save.** Saving a config resolves the snapshot, computes
the hash, and — if no existing successful build record matches the hash +
base version — fires a build immediately. The user sees the config go
straight to Building in the selector.

Controls on when a save does and does not fire a build:

1. **Selection-change-gated.** Editing only the friendly name, or
   re-saving an identical selection, does not rebuild. The trigger is "the
   resolved snapshot has no existing successful build record for this hash
   + base version."
2. **Identical Rejected combo not rebuilt.** Re-saving a config whose
   snapshot matches an existing blocklisted combo does not fire a build —
   it stays Rejected. No point burning two more runs on a known-bad combo.

**Build-on-save, not build-on-launch, is the load-bearing choice.** It
means a workspace can only ever be launched against a Ready image, which is
what lets the controller stay genuinely untouched (no `PendingImage` phase,
no build-wait state, no API-writing-workspace-status). The cost is that
every saved *novel* config fires a real multi-arch build, including configs
that are never launched.

Rate-limiting is **intentionally not built in v1** — public repos have
generous GitHub Actions limits. If measured usage warrants it, the controls
to add are: per-user novel-build limits (N/hour), org quotas on published
configs, and a debounce window (coalesce rapid saves). Tracked in
open items.

### API-owned image lifecycle

Because builds are eager and configs are only launchable when Ready, the
entire image lifecycle runs inside the API. The workspace controller sees
nothing about builds — it only ever receives a final, ready image ref in
`Workspace.spec.image`, exactly as today. No new phase, no new condition,
no status write-back. The existing `Pending` / `Creating` flow is reused
unchanged.

## Build execution: GitHub Actions

A workflow (e.g. `.github/workflows/image-build.yml`) triggered by
`workflow_dispatch`, parameterized by the snapshot + base version. It:

1. Renders a deterministic Dockerfile from the snapshot + resolved base
   version (pure function — identical snapshots always render an identical
   Dockerfile, so a content-addressed tag maps to exactly one reproducible
   build).
2. Builds multi-arch via `docker buildx`, for the architectures the platform
   owner has configured (`architectures` in the catalog seed). The platform
   owner controls this because they control what compute is available —
   there is no point building for arm64 if no arm64 nodes exist.
3. Pushes to ghcr.io (GitHub hosts storage; we host nothing extra).
4. On success: records the digest against the build; config → Ready.
5. On failure: records the failure_reason; the API schedules the next
   attempt (up to 3) or, on the 3rd failure, invokes the failure-handling
   seam.

Builds are replaceable and stateless — losing a run and re-triggering
produces the same image. The GitHub-hosted runner is ephemeral, so the
builder is untrusted-by-default and isolation is inherited from GitHub
Actions. No custom builder VMs to harden.

### Reconciliation on API restart

Build state lives in Postgres (`image_factory_builds`); execution lives in
GitHub Actions. If the API restarts mid-build, in-flight rows sit at
`building` with a `gh_run_id`. On boot, a sweep checks each in-flight
`gh_run_id` against the GitHub API and reconciles: marks succeeded/failed
as appropriate, schedules the next attempt or invokes the failure seam. No
build is orphaned by an API restart.

## Failure-handling seam: platform-LLM explanation

Build failures are never shown raw to the user. The handling path (runs
only on the **3rd/final** attempt, not the transient first two):

1. The GH Action failure step captures the log tail and POSTs it to the API
   against the build ID.
2. The API calls the platform's existing LLM infrastructure (the cluster
   already runs LiteLLM/vLLM) for a summary + suggested next action.
3. The summary is stored against the build record; the `(extension_set,
   base_name)` is written to `image_factory_blocklist`; the config flips to
   Rejected; and the user is notified with the explained rejection: "this
   combination isn't supported: <reason>."
4. Optional: an "investigate in a workspace" button spins up a workspace
   pre-loaded with the build context + error log — dogfooding the platform
   to debug itself for hard cases. Not the default path.

**Attribution rule.** The LLM is asked whether a *single* extension is at
fault (e.g. a typo'd apt package). If it can attribute confidently, that
extension is flagged for admin review (a comment on the extension row, not
an automatic retire — admins decide). If it cannot attribute (the failure
is a genuine combination conflict), the row goes to the combination-level
blocklist. Conservative default: when the LLM is uncertain, block the
combination (over-block is recoverable via admin un-block; under-block
re-surfaces the failure to another user).

This reuses the existing LLM stack; no new component. The LLM never sees
secrets (there are none in snapshots or build context).

## Settings → UX

**Settings page ("Workspace Images"):**

1. User browses the catalog (extensions + versioned bases), read via
   `GET /v1/image-factory/catalog`.
2. Assembles a selection by checkbox/dropdown. Blocklisted combos render
   greyed with "not supported."
3. Names it ("ml-stack"), saves → `POST /v1/image-factory/configs`
   resolves the snapshot, computes the hash, stores `(owner, name,
   selection, snapshot, hash)`, and fires a build. Config is immediately
   shown as Building.
4. The config transitions Building → Ready (or → Rejected with the LLM
   explanation) asynchronously; the selector pill updates via the existing
   SSE event infra.

**Launch dialog:**

1. Image picker shows: my configs + my org's published configs + platform
   configs, each by friendly name.
2. Policy gate: if org policy is `published_only`, the member sees only
   org-published + platform configs (cannot assemble, though the catalog is
   still viewable).
3. Each config shows a status pill: **Building** (greyed out, not
   launchable, with ETA/progress via SSE), **Ready** (launchable), or
   **Rejected** (greyed out, not launchable, with the LLM explanation and
   the "investigate in a workspace" button).
4. User picks a Ready config and launches. The workspace starts against an
   already-built image — no build wait at launch time.

UX cost accepted: a novel config is not launchable for ~10 minutes after
save (the build window). That is the trade for eager builds + an untouched
controller. Users are never blocked *at launch* — they see Building
up-front in the selector.

## Open items (deferred, not blocking)

- **Rate limits / quotas** — intentionally not built in v1 (public-repo GH
  Actions budget is generous). Revisit if measured usage warrants:
  per-user novel-build limits, org quotas, debounce windows.
- **"Newer base available" affordance** — optional future UI signal; v1
  has no `stale` state and no auto-migration. Existing configs stay on
  their pinned base version until re-saved.
- **Registry GC** — no retention policy in v1; revisit when storage growth
  is measured.
- **Org-owner quota on published configs** — whether an org can publish
  unboundedly or is capped.
- **Webhook vs polling** for GH Actions build status (webhook preferred but
  needs a public endpoint; polling is the safe default).
- **Catalog contribution path** — whether verified community-contributed
  extensions can land in the catalog via PR (currently operator-only).
- **Build timeout** — a GH Actions run that hangs (stuck runner, GH
  outage) leaves a build at `building`. Need a max-duration after which the
  attempt is treated as failed (counts toward the 3-attempt budget) and the
  next attempt is scheduled. Exact duration TBD in the build-workflow
  story.
- **Secret scanning on `type: file`** — the one place an operator could
  accidentally bake a secret into an image. Defense-in-depth: run
  gitleaks/trivy on the rendered build context in CI. Wire into the
  build-workflow story.
- **`RuntimeEnvironment` creation policy** — does launching a factory
  config auto-create a `RuntimeEnvironment` CR per config, or does the
  workspace reference the image ref directly (bypassing RTE)? Resolve in
  the controller-integration story.

## Decisions summary

| # | Decision | Rationale |
|---|---|---|
| 1 | Opaque SHA hash, decode via API lookup | Talos model; avoids in-band/secrecy problems of self-describing tokens |
| 2 | Hash is over the resolved-value *snapshot* + base *name*; base *version* is a separate axis | Content-addressed (survives extension edits) AND version-stable (Talos model) |
| 3 | Image tag = `s-<hash>-<baseVersion>`; CRD points at full ref | No CRD indirection; version explicit |
| 4 | No standalone factory service — API + GH Actions only | No runtime state justifies a second process |
| 5 | Selection-only (no free text, no `run`, no `env`) | Eliminates injection / arbitrary-build-exec surface |
| 6 | No secrets in schematics/images/hash | Stays in existing K8s-Secret injection path |
| 7 | Catalog in PostgreSQL, seeded from `catalog.seed.yaml` at boot | Blocklist must be runtime-mutable; single runtime source of truth |
| 8 | Snapshot resolved values into the config at save time | Admin edits change the hash for new configs only; existing configs frozen; decode is exact forever |
| 9 | Bases are append-only by `(name, version)`; extensions are mutable in place | Bases genuinely version over time; extensions edits aren't version-worthy |
| 10 | Open catalog + auto-growing blocklist (model b) | Low maintenance; explained first-time failures accepted |
| 11 | Retry up to twice (3 attempts) before Rejected | Separates transient from genuinely bad; blocklist only grows on real failures |
| 12 | Build trigger is eager (on save, selection-change-gated) | Configs only launchable when Ready → controller genuinely untouched |
| 13 | Controller genuinely untouched — no new phase, no condition | API owns the image lifecycle; workspace only ever sees a ready image ref |
| 14 | Config states: Building / Ready / Rejected; workspaces have no build/failed state | Failures surface on configs, never on workspaces |
| 15 | No user-facing retry; Rejected → edit-and-re-save or admin un-block | Users never concerned with retrying; known-bad combos not re-burned |
| 16 | Org policy: `assemble` or `published_only` | Full policy space given dropdown-only input |
| 17 | Friendly names: member > org > platform scope | No global namespace to collide |
| 18 | Failure explanation via platform LLM; conservative attribution | Reuses existing stack; over-block recoverable, under-block not |
| 19 | GitHub Actions builds, ghcr.io storage | Free hosting, replaceable, ephemeral runners |
| 20 | No GC, no rate limits in v1 | Accept unbounded growth + generous public-repo budget until measured |
| 21 | Platform owner configures build architectures (`platform_config.architectures`) | Platform owner controls what compute is available; no point building for archs with no nodes |
