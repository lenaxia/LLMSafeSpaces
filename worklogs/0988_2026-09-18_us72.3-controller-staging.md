## Design decisions (settled this session)

### D1 — Credential source seam: a minimal API internal endpoint (unavoidable, implemented)

The controller must seal **plaintext** provider keys, but decrypted BYO credentials
exist only transiently inside the API (Postgres rows are ciphertext; K8s holds none of
them). No existing surface serves the controller:

- `pod-bootstrap` returns decrypted data but is authenticated by the **pod's** projected
  SA token (TokenReview) — the controller holds no such token, and the response shape is
  batch entries, not the provider list.
- `GET /api/v1/internal/orgs/:id/status` is org metadata only.

Settled seam (the OrgStatusClient precedent, verbatim pattern):

- **API side (new, small):** `GET /api/v1/internal/workspaces/:workspaceID/llm-providers?ownerUserID=<uid>`
  — constant-time `X-Internal-Token` (`LLMSAFESPACES_INTERNAL_TOKEN`, fail-closed 403
  when unset, 401 on mismatch — identical to the org-status handler), backed by a new
  `SecretService.ResolveLLMProviders(ctx, ownerUserID, workspaceID)` that reuses
  `loadWorkspaceRows` + `decryptBindingWithDEK` + `applyModelAllowlist` with the same
  dedup-by-slug-first-winner semantics as the batch builder, so the staged set is by
  construction exactly the batch's provider set. Every reveal is audited
  (`internal_llm_providers_reveal`).
- **Controller side:** `CachedLLMProviderSource` (30s TTL, success-only cache — a fetch
  failure fails the staging pass loudly; no stale-serve, unlike org status: credentials
  must be fresh and a stale set could seal revoked material).

K6 is unaffected: this is controller→API trusted-plane, never a pod delivery path.
Documented as required by the story ("if a small API-side internal endpoint is
unavoidable, implement it and document why").

### D2 — Token handoff Secret (shape owned here, consumed by US-72.4)

- Name: `workspace-relay-<workspaceName>` in the **workspace namespace**, owner-ref'd to
  the Workspace (GC on terminate, survives suspend).
- Single data key `handoff`, one JSON document:

```json
{
  "revision": "<staged revision>",
  "routerURL": "http://llm-relay-router.llm-relay.svc.cluster.local",
  "providers": [
    {
      "providerSlug": "openai",
      "kind": "openai",
      "token": "lrt_...",
      "routerPath": "/w/<workspaceName>/<slug>/v1",
      "baseURL": "https://api.openai.com/v1",
      "modelAllowlist": ["gpt-4o"],
      "keyID": "hpke-g2",
      "expiresAt": "2026-09-19T07:00:00Z"
    }
  ]
}
```

- **Staged revision** = deterministic content hash (`sha256` over sorted
  `slug|envelope|token-expiry` per provider, hex[:12], `r`-prefixed) — changes exactly
  when any envelope or token changes, so US-72.4 can compare it against `spawned_rev`,
  and `CredentialsStaged` carries it in its message.
- Renewal: a token is re-minted when it is past TTL/2 (design §4.4); the mint check is
  in-pass on every Active reconcile (requeue cadence 15s), zero API calls at steady state.

### D3 — Envelope Secret contract (matches the router's informer cache exactly)

`byo_cache.go` already fixes the read-side contract; this story writes it:
name `llm-relay-env-<workspaceName>-<slug>` (slug is already `^[a-z0-9-]+$` by the DB
CHECK), labels `llmsafespaces.dev/workspace-id: <workspaceName>` +
`llmsafespaces.dev/provider-slug: <slug>`, data `envelope` (the `stg:v1:…` wire string)
+ `models` (JSON array of allowlisted model IDs — the router's zero-upstream `/models`
catalog). The mint-key Secret (`llm-relay-mint-key`, data key `mint-key`) is created by
the controller (adopt-if-exists) — `byo_run.go` documents that expectation.

### D4 — Staging mode: HPKE now, KMS loud-not-yet

The controller resolves its sealer from `llm-relay-hpke-pub` (it has `get` RBAC on
exactly that Secret). If the pub Secret is absent but a `llm-relay-kek` Secret exists,
the pass fails loudly with CredentialStale — KMS staging mode additionally requires
RootKeyProvider construction in the controller (cloud credential plumbing that does not
exist controller-side today; neither US-72.2's router wires it — the fleet runs
HPKE-only). Landing KMS construction is flip-prep work (US-72.5); the seam
(`StagingSealer` interface) means no structural change later.

### D5 — Kind coverage: stage only HTTP-frontable kinds

The BYO router is a Bearer-injecting reverse proxy to exactly one upstream. That covers
the plain-REST kinds. `pkg/secrets.ProviderDefaultBaseURL(kind)` (new, single table next
to `LLMProviderData` so US-72.4's builder swap reuses it) resolves first-party defaults:
openai, anthropic, google, cohere, mistral, perplexity, groq, xai, openrouter, together;
`openai_compatible` requires an explicit BaseURL. NOT staged (event + named in the
`CredentialsStaged` message, raw-key path continues — mixed-fleet semantics):

- `bedrock`, `vertex`, `azure_openai` — SDK-shaped auth (SigV4/GCP/OAuth token
  exchange); a Bearer-injecting proxy cannot speak them by construction.
- `opencode` (zen) — auth-store merge path, `shouldSkipRelay`'s concern (US-72.4
  verified orthogonal).

K1 full coverage for these kinds is a US-72.5 flip-gate question, flagged in the PR.

### D6 — Staleness classification + escalation predicate (§4.2, controller-homed)

Recomputed fresh each pass, cause → class:

| Cause (observable now) | Class | Escalates? |
|---|---|---|
| pub Secret unparseable/missing (seal-time parse fails loudly) | corruption-adjacent (`PubUnreadable`) | no (router-side watch assert self-heals keypair corruption; controller cannot compare generations against an unparseable pub) |
| agentd degrade `credential_stale` (the router's resolve-failure code — wrong/corrupt keypair lineage, §4.2's one escalating cause; live emission lands with US-72.4's degrade codes) | corruption | **yes** (with lineage + anti-storm) |
| handoff token past expiry / mint failure | token-expiry | no (renewal owns) |
| provider unbound this pass (envelope deleted, D2) | revocation | no (terminal by design) |
| batch/#852 deferral, `relay_unreachable`, unknown codes, spawned_rev behind staged revision | delivery | no |

Lineage-intact conjunct (the `spawned_rev`-class terminal signal, NOT the batch-apply
anchor): all desired envelopes present AND
`ws.Status.SecretsDelivery.SpawnedRev == current staged revision`. Pre-US-72.4 pods
never satisfy it (their spawned_rev tracks the raw batch) — so escalation is
structurally suppressed until the builder swap makes the signal real; the predicate and
its tests land here, per the story.

Anti-storm bound: cluster-global (rotations are cluster-wide), persisted as the
`llmsafespaces.dev/last-rotate-escalation` annotation on the `llm-relay-mint-key`
Secret — shared across workspaces and across controller restarts; escalation spaced
≥10m (the prior-key retention default).

### D7 — Condition lifecycle choices

`CredentialStale(revocation-class)` is raised on the pass that performs the envelope
deletion and clears on the next clean pass (one-pass visibility; the durable post-72.4
signal is the agentd `credential_stale` degrade feeding the same condition). Staging
failures are never fatal to phase progression pre-flip (the raw-key path still
delivers): they surface as conditions + events + requeue. `CredentialRejected` is set
from router rejection telemetry (degrade codes `scope_violation` /
`sanitization_refused` / `quota_exceeded`; emission lands with US-72.4) + a Warning
event, per §4.7 "violations are CredentialRejected-class events, never silent".

### D8 — Persistence of staging state

Per-workspace annotations on the Workspace (`llmsafespaces.dev/relay-sealed-generation`,
`…-staged-revision`), written only on change (no reconcile hot-loop); global
rotate-escalation timestamp on the mint-key Secret (D6). Fallback for a lost
sealed-generation annotation: derive from the live envelopes' keyIDs
(`InspectStagingEnvelope`), so a wiped annotation cannot wedge re-seal.
