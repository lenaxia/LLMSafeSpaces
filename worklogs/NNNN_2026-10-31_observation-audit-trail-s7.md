## 1. The finding this closes

Reconstructing what the platform DID during the incident — were nudges sent? did lapse verdicts fire? who reclaimed? — required transcript forensics across five sessions, and the orchestrator (no fault of its own) asserted a FALSE "heartbeat-extended" message because the truth was unobservable. ## 2. What was built

1. **Migration 000055 `task_observation_events`** (api + helm mirror): bigserial id, task_id FK CASCADE, kind, session, detail JSONB, created_at; indexes `(task_id, id DESC)` (the window read) and `(created_at)` (the TTL prune arm). Deliberately SEPARATE from `board_events`: that table is the idempotency ledger (requestId-keyed, replay-semantic, SSE-projected — unprunable, and renewals there would flood SSE); this table is a prunable working window.

3. **The six kinds, at their write points**:
   - `stamped` — both landing paths (spawn write, claim-evidence back-fill), detail `{origin, lag_seconds}` (S1's stamp_lag as a per-task fact).
   - `nudged` — the rc1 post-commit loop (obsNudged), detail `{nudge_id, rung}`; the rung is set at `send()` time where the row's pre-existing sentinel answers it (`first_sentinel` vs `re_anchor` — an unmeasured ordinal question re-anchors, never guesses). The bus stays the single ephemeral nudged publisher (S4's no-double-report rule holds — the TRAIL is a different plane, and "were nudges sent?" was the incident's first unanswerable question).
   - `renewed` / `lapse_verdict` / `reclaimed` — through `emitLease` itself (one seam: trail row FIRST, then the bus sink — the durable truth does not wait on a remote bus), so the rc1 loop AND both persona-pass sites AND the heartbeat-response arm (its own write, stage.go) all ride automatically. The rc1 renew-arm's "renewals never flood the trail" comment was corrected: renewals never flood the IDEMPOTENCY LEDGER; the retained window takes them (bounded by the boundary).
   - `deposed` — after the depose commit; detail carries the salvage pointer verbatim + `from_stage` + `requeued`; a replayed requestId skips the duplicate row.
4. **The read surface**: `Health` grows `observation_events` (window: newest 30 across the caller's boards, newest first, short id attached, sessions phrase-translated with raw+flagged degrade — `translateHealthObservations`, the `translateHealthLeases` mirror) and `observation_retention` (the boundary self-documented on every read). Owner scope (`p.user_id`) and agent scope (`p.target_workspace_id`) both filled through one shared `healthObservationEvents(scope, arg)`. Additive JSON on the existing struct — rides MCP `board_health`, `board_read`+`health=true`, the REST endpoint, and the agent-surface projection with NO handler/loopback/agentd signature changes; the spec and SDK twins stay truthful (`sdks/openapi.yaml` BoardHealthObservation + BoardHealthObservationRetention schemas, the Go/TS `BoardHealth` mirrors — additive only). Tool descriptions updated where the window is named (`board_health`, `board_read`'s health flag) + the docs row.
5. **The retention boundary** (documented in `docs/operator/monitoring.md`, self-documented on every read): per-task cap 50 newest, TTL 14 days, enforced by the reconciler's sweep at most hourly (`maybePruneObservations` — wall-clock gate, idempotent DELETE, pruned-row counter). Older truth stays in `board_events`'s nudge/wedge/reclaim/depose action rows — the boundary never touches the ledger.

## 5. What was deliberately NOT done

- **No per-task filter argument on `board_health`** — the charter offers "extend board_health OR a per-task audit read"; the additive window satisfies it at zero signature cost. `Service.TaskObservationTrail` is the per-task read, public for whichever surface wants it next; threading a filter arg through MCP client → loopback → REST → interface → mocks is a whole-lane blast radius for marginal gain, in exactly the files the pending merges conflict.
- **No design-0072 amendment** — 0072's roadmap tracks bus consumers; S7 is not a consumer (it records at the decision seams the engine already owns). The plane relationship (ledger / bus / retained window) is documented in observation.go's header and monitoring.md.
- **No frontend health-panel rendering** — the orchestrator surface is the MCP/REST read; the panel can render `observation_events` when a human asks for it.
- **No summarization job for aged-out rows** — "older summarized or pruned per platform conventions": the summary IS the board_events ledger (already written, already permanent); a separate summarizer would duplicate it.
