**Date:** 2026-08-01

1. Determine whether upgrading the opencode version pin (v1.15.12 → v1.18.10) is safe — i.e., non-breaking against LLMSafeSpaces' proxy contract.

## The v1 → v2 transition: intent and timing

Evidence that v2 is intended to replace v1 (eventually):

- The upstream default branch is `2.0`.
- On `2.0`, the legacy `packages/opencode/src/server/routes/instance/httpapi/` package is **entirely deleted** (79 files removed). The transitional `packages/server/` (Effect HttpApi-based, present in v1.18.10) is also gone — consolidated back into `packages/opencode/src/server/instance/`.
- 2.0 rewrites the server back to **Hono** (from Effect HttpApi). The framework has now changed twice (Hono → Effect HttpApi in v1.3 → back to Hono in 2.0).
- **Route *paths* are preserved across all three generations.** `SessionRoutes` still mounts at `/session`; `/prompt_async`, `/abort`, `/global/health`, `/event` all survive into 2.0. The wire-level contract is stable; only the implementation framework churns.

**Implication for LLMSafeSpaces:** even when 2.0 ships as stable, the proxy contract survives. What changes is the maintenance story upstream (legacy codepaths get deleted, forcing anyone still on v1.15-era code to move to the equivalent paths in the new server). v1.18.10 is the bridge release — v1 and v2 served side-by-side. There is no announced removal date for v1.

## Strategic assessment — can v2/SDKs remove the `agent-config.json` architecture?

**Short answer: no, not yet.** Rule 12 (contain before abstraction) applies — the forcing function has not arrived.

### What the v2 API offers

v1.18.10 serves two path namespaces side-by-side. Legacy paths (`/session`, `/provider`, `/event`) retained; v2 adds a canonical `/api/*` namespace:

- `/api/session/{id}/event` — per-session event stream (vs global `/event` requiring workspace filtering)
- `/api/session/{id}/interrupt`, `/context`, `/history` — structured session ops
- `/api/integration/{id}/connect/key` + `/connect/oauth` — **server-managed provider credentials**
- `/api/credential/{id}` (update/remove) — credentials as first-class resources
- `/api/permission/request` + `/saved` — structured permission management
- `/api/pty/{id}/connect-token` — token-gated PTY auth
- `/api/model`, `/api/provider` — canonical catalogs

### The integration API — deepest investigation

The hypothesis was: if `/api/integration/*/connect/key` lets us POST a provider key and have opencode manage storage + config generation internally, we could delete the `AgentConfigWriter` and the entire relay-config subsystem.

**Finding: it does not.** Full chain traced:

1. `Integration.ID` is an open branded string (`Schema.String.pipe(Schema.brand("Integration.ID"))`) — not a closed enum. Any ID works.
2. The integration registry is **plugin-driven**. Built-in integrations (OpenAI, Anthropic, the `opencode` Console/Zen device-flow) are registered by **plugins** at boot (`packages/core/src/plugin/provider/*.ts`). Each plugin registers: an `Integration` (auth method) + a linked `Provider` (defines `request.body.baseURL`, models), joined via `provider.integrationID`.
3. `POST /api/integration/:id/connect/key` stores a key credential **only if** an integration with a `KeyMethod` is already registered by a plugin. It does **not** create the integration or declare a `baseURL`. The HTTP API is a credential *store*, not a provider *declarator*.
4. The bridge that makes custom providers work today is the **v1 config block** (`packages/core/src/config/plugin/provider.ts`). The `ConfigProviderPlugin` reads the legacy `provider: { myid: { options: { apiKey, baseURL }, models } }` from `agent-config.json` and materializes it into both the v2 catalog (provider + models + baseURL) and the v2 integration registry. So a custom provider declared in config is automatically available in the v2 API — but you cannot rotate its key via `/api/integration/*/connect/key` unless a plugin registered a `KeyMethod` for it.

**Implication:** the v2 integration HTTP API does **not** eliminate the `agent-config.json` write architecture. The only way to give opencode a custom provider with a custom `baseURL` today is still the config file (or writing a TS plugin, which is more code, not less). The forcing function for deleting the relay-config subsystem has not arrived.

### What v2/SDKs *can* help with (lower-value wins)

| Win | Mechanism | Effort |
|---|---|---|
| Retire wire-format reverse-engineering class of bug (cf. #486, worklogs 0070/0122/0231/0234/0566/0569/0570) | Adopt the published `openapi.json` as codegen input for a Go client over the legacy paths | Medium; no architectural change |
| Fix frontend "undefined" error display (worklog 0070 IMPACT 7) | v2 declares explicit `Schema.ErrorClass` contracts per endpoint | Small; needs v2 client |
| Typed SSE payloads | Per-session `/api/session/{id}/event` + documented event schemas | Small; doesn't change SSE framing |

### Recommendation

1. **This upgrade (v1.15.12 → v1.18.10):** bump pins only, stay on legacy paths. Low risk, buys time, picks up MCP hardening relevant to Epic 53.
2. **Near-term (independent of version):** adopt `packages/sdk/openapi.json` as codegen input for a Go client covering the legacy paths already proxied. Cheap, reversible containment move (Rule 12).
3. **Strategic spike (when 2.0 ships stable):** re-evaluate whether `/api/integration` or a successor supports custom providers with custom baseURL. Only then does deleting the relay-config subsystem become viable.

The worst move would be to build a "v2 agent provider abstraction" today against a single consumer (Rule 12's explicit anti-pattern).
