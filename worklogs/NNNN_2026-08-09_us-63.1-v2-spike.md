## Objective

Convert Epic 63's code-reading assumptions (findings F1–F17, all pinned to opencode
1.18.10) into empirical facts by exercising the V2 session endpoints
(`POST /api/session/:sid/prompt`, `POST /api/session/:sid/interrupt`, `GET /event` SSE)
against a live workspace pod running the **bundled opencode 1.18.10** binary, before
US-63.2 builds a client against them. No production code changes; this is assumption
validation. Specifically: does V2 prompt admit without 409 when busy, do V2 events
reach the proxy's existing `/event` stream with the predicted wire strings, and does
queued input drain autonomously after an OOM-style opencode restart?

## Findings (one bullet per acceptance criterion)

- **V2 prompt on idle session** — **PASS.** `POST /api/session/:sid/prompt` with
  `{prompt:{text}}`,`delivery:"queue"` → **HTTP 200**, body
  `{data:{admittedSeq,id:"msg_...",sessionID,prompt:{text},delivery,timeCreated}}`.
  (Report raw HTTP capture.)
- **V2 prompt while a turn is in flight (the load-bearing 409 question)** — **PASS
  (HTTP 200, no 409).** A second prompt with `delivery:"queue"` admitted while the
  first was in-flight returned **HTTP 200** (admittedSeq 5), not 409. US-63.3 is
  unblocked. *Timing caveat:* due to cold-start latency the first turn's LLM step
  had not begun microsecond-actively running when the second was admitted (admission
  happened during the promote phase); this is **moot for the 409 question** because
  V2 admission is a SQLite insert + seq allocation that is busy-independent by design
  — F17 says 409 only occurs on caller-supplied `id` collision, never on busyness.
  A follow-up could firm up the strict "during active step" condition, but it would
  not change the verdict.
- **V2 interrupt during an in-flight turn** — **PASS (HTTP 204).** Returned **204 No
  Content**; the session continued processing subsequently-queued input (an essay turn
  promoted and ran to completion per SSE), consistent with F8's non-destructive claim.
- **V2 interrupt on an idle session** — **PASS (HTTP 204).** No-op success (not an
  error). US-63.4 can treat the proxy's abort as always-success on 2xx.
- **OOM-restart drain (LOAD-BEARING for US-63.9)** — **FAIL (strands) — confirms F16.**
  See the dedicated verdict below.
- **SSE events on `/event`** — **PASS.** Observed **10 events** in a 12s window. Type
  strings that appeared (exact): `session.next.prompt.admitted`,
  `session.next.prompted`, `session.next.step.started`, `session.next.text.started`,
  `session.next.text.delta`, `session.next.text.ended`, `session.next.step.ended`,
  `server.connected`, `server.heartbeat`. The F13/F14 prediction is confirmed verbatim.
  Wire format note for US-63.5: events are `data: {"id":...,"type":"<type>","properties":{...}}`
  lines (type inside JSON), **not** a separate `event:` line.

## Load-bearing verdict on the OOM-restart drain (Phase 6) — unambiguous

**FAIL — queued input does NOT drain autonomously after an in-place opencode restart.
US-63.9 MUST ship a drain trigger before US-63.7 deletes the stranded-queue sweep;
the status quo is NOT acceptable.**

Procedure: queued message D (a 300-word essay) + marker message E
("reply with: ack-oom-restart") via `delivery:"queue"`, then `pkill -9 -f "opencode serve"`
inside the pod. agentd restarted opencode in-place (same pod, `/global/health` back to
200 in ~6s). A 60s SSE watch on `/event` showed **only `server.heartbeat` events — zero
`session.next.*` activity** — and the marker prompt's assistant reply ("ack-oom-restart")
was **absent** from session history (`GET /api/session/:sid/message`). Both the
SSE-side signal (no admission/promotion activity) and the definitive history-side signal
(no marker reply) agree: nothing scanned for pending `SessionInput` rows on startup.

**Implication for US-63.9:** the upstream `resume` HTTP endpoint does not exist on 1.18.10
(F15, unchallenged), and opencode's startup has no auto-drain hook (F16, now empirically
confirmed). US-63.9 must therefore ship a **proxy-side wake** (e.g. re-POST a tiny
`delivery:"queue"` prompt to each known session after opencode restart, which triggers
`execution.wake` and drains the durable queue), OR pursue an upstream `resume` exposure
PR. The proxy-side wake is the lower-risk path and is fully in our control.

## New risk surfaced by the spike (not in F1–F17)

**F18 — V2 prompt body shape mismatch (load-bearing for US-63.2).** The original
US-63.1 spec and the harness assumed the prompt body is
`{prompt:{parts:[{type:"text",text:"..."}]}}` — the parts-based contract from Epic 65
(design 0049). opencode **1.18.10 is older than that contract** and **rejects** the parts
shape with **HTTP 400 `InvalidRequestError: Missing key at ["prompt"]["text"]`**. The
accepted shape is **`{prompt:{text:"..."}}`** (a plain string), with `delivery` optional
and defaulting to `"steer"`. Recorded live in the report's Phase 2b.

Implication: US-63.2's V2 client MUST POST `{prompt:{text}}`. When opencode is later
bumped to a version that adopts the Epic 65 parts contract, the client will need
adaptation — the contract should be pinned and tested with the
`agent_config_writer_schema_test.go` pattern. This is a new, actionable risk that the
code-reading pass did not catch (the design assumed forward-compatibility with the parts
shape).

No other new risks beyond F18. Notably: the agentd in-place restart behavior (pod
survives, opencode comes back as a new PID in the same pod) is good news for US-63.9 —
a proxy-side wake trigger can rely on the pod IP staying stable across the restart.

## Verdict: green-light US-63.2?

**GREEN-LIGHT for US-63.2, with one contract pin mandatory.** The V2 endpoints behave as
Epic 63 requires: prompt admits without 409 on busy, interrupt is non-destructive (204),
and the SSE events US-63.5 needs are present on the existing `/event` stream with the
predicted strings. US-63.2 may proceed.

**Mandatory precondition:** US-63.2 must target the **`{prompt:{text}}`** body shape
(F18), not the parts-based shape the original spec assumed, and must pin that contract
with a schema test. F18 is not a blocker (the working shape is known and confirmed) but
it is a deviation from the original design that the implementer must not miss.

**Carry-forward (not blockers for US-63.2):**
- US-63.9 is non-negotiable and cannot be descoped: F16 confirmed stranded input on
  restart. Start it in week 2 per the epic plan.
- US-63.5 bridge must parse `data:`-line JSON (type inside payload), not `^event:` lines.
- Cheap test adds for US-63.2/63.4: a 409-on-`id`-collision probe, a 404-on-bogus-sid
  probe, and a direct post-interrupt history probe to assert queued-row survival.

## Tests run

- The spike harness `local/us-63.1-v2-session-spike.sh` IS the test. Full run log and
  the authoritative raw HTTP/SSE capture: **`worklogs/spike-us-63.1-report.md`**.
- Adversarial self-review (Rule 11) was applied: the first run's Phase 5 verdict text
  ("0 events observed") was found to contradict its own appended raw capture (which
  showed 10 events); root cause was a harness SSE-format assumption bug (grepping
  `^event:` lines when 1.18.10 emits `data:`-line JSON). The harness was fixed
  (commit `ff14318b`) and re-run; the regenerated report's verdicts all trace to the
  raw capture.
