## Objective

**US-63.5:** Map opencode's V2 session events (`session.next.prompt.admitted`/`session.next.prompted`) to the `queue.update` SSE taxonomy (`enqueued`/`sent`) so the frontend queue-pill UX works without changes under the V2 flag.

**US-63.9:** After a pod restart (OOM, kill, rolling update), drain queued input that strands in opencode's durable SQLite because nothing triggers `execution.wake`. The spike (worklog NNNN_us-63.1-v2-spike) confirmed F16 empirically: queued input does NOT drain autonomously.

---

## Work Completed

### US-63.5 — SSE Event Bridge

**`onRawEvent` integration** (`proxy_events.go:206-209`): when `v2SessionQueueEnabled`, calls `onV2RawEvent` which detects V2 event types and synthesizes `queue.update` events.

**`onV2RawEvent`** (`proxy_v2.go`):
- `session.next.prompt.admitted` + `delivery:"queue"` → `publishQueueEvent(wid, sid, "enqueued", messageID, "")` + tracks session in `v2Pending`
- `session.next.prompted` + `delivery:"queue"` → `publishQueueEvent(wid, sid, "sent", messageID, "")` + removes from `v2Pending`
- Steer delivery is ignored (not a queue entry)

**`enqueueV2` change:** no longer calls `publishQueueEvent` itself. The `enqueued` event is derived purely from the V2 `PromptAdmitted` event — eliminates the race where `enqueued` fires before opencode has actually admitted the input.

### US-63.9 — Stranded-Input Recovery

**`v2PendingSessions`** (`proxy_v2.go`): in-memory `map[workspaceID]map[sessionID]bool` tracking sessions with undrained V2 queue-delivered input.
- Added in `enqueueV2` (on successful admission) and `bridgeV2Admitted` (on V2 PromptAdmitted event)
- Removed in `bridgeV2Prompted` (on V2 Prompted event — input was promoted/drained)

**`wakeStrandedV2Sessions`** (`proxy_v2.go`): called from `reconcileSessionState` on SSE reconnect. For each tracked idle session, POSTs a minimal `delivery:"queue"` prompt (`"\n"`) to trigger `execution.wake` → `runner.run` → drains all pending rows.

**Trade-off (Option B):** the wake prompt creates one extra turn per session. This is the accepted trade-off of the proxy-side wake approach — it pollutes the session with one no-op turn but unblocks all stranded queued input. The clean solution (Option A: upstream `POST /api/session/:sid/resume` endpoint) would not create a turn; it is a follow-up if/when opencode exposes it.

---

## Key Decisions

1. **Derive `enqueued` from V2 events, not from `enqueueV2`.** The AC says "eliminating the race where enqueued fires before opencode has actually admitted." `enqueueV2` gets a 200 from `PromptV2` — but the V2 `PromptAdmitted` event is the authoritative signal that opencode has admitted the input. Deriving from the event is race-free.

2. **In-memory tracking, not Redis.** Per-replica tracking is sufficient for the SSE-reconnect case (same replica handles the workspace's event stream across reconnects). Multi-replica failover (original replica dies) is an accepted edge case — messages strand until the user's next prompt, same as the current behavior for that edge case. A Redis-backed set would be the US-45.x pattern but is premature for a feature-flagged path.

3. **Option B (proxy-side wake) over Option A (upstream resume).** Option A requires contributing to opencode's upstream repo (small PR exposing `POST /api/session/:sid/resume`). Option B is fully in our control and works today. The trade-off (one no-op turn) is documented; the clean upstream fix is tracked as a follow-up.

4. **`"\n"` as the wake prompt text.** Must be non-empty (F18: opencode rejects empty text). A newline is minimal pollution — the LLM processes it as a blank, the stranded input drains. A space character would work equally well.
