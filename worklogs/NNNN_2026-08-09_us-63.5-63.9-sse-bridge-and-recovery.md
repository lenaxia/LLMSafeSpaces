## Objective

**US-63.5:** Map opencode's V2 session events (`session.next.prompt.admitted`/`session.next.prompted`) to the `queue.update` SSE taxonomy (`enqueued`/`sent`) so the frontend queue-pill UX works without changes under the V2 flag.

**US-63.9:** After a pod restart (OOM, kill, rolling update), drain queued input that strands in opencode's durable SQLite because nothing triggers `execution.wake`. The spike confirmed F16 empirically.

---

## Work Completed

### US-63.5 — SSE Event Bridge

**`onRawEvent` integration** (`proxy_events.go`): when `v2SessionQueueEnabled`, calls `onV2RawEvent` which detects V2 event types and synthesizes `queue.update` events.

**`onV2RawEvent`** (`proxy_v2.go`):
- `session.next.prompt.admitted` + `delivery:"queue"` → `publishQueueEvent(wid, sid, "enqueued", messageID, "")`
- `session.next.prompted` + `delivery:"queue"` → `publishQueueEvent(wid, sid, "sent", messageID, "")` + decrements `v2Pending`
- Steer delivery is ignored (not a queue entry)

**`enqueueV2` change:** no longer calls `publishQueueEvent` itself. The `enqueued` event is derived purely from the V2 `PromptAdmitted` event — eliminates the race where `enqueued` fires before opencode has actually admitted.

**`bridgeV2Admitted` does NOT track sessions** — only `enqueueV2` is the tracking site. The V2 event is the SSE signal, not the tracking signal. (Initial implementation double-counted: enqueue + event = 2 per message. Fixed in review cycle 2.)

### US-63.9 — Stranded-Input Recovery

**`v2PendingSessions`** (`proxy_v2.go`): in-memory reference-counted `map[workspaceID]map[sessionID]int` tracking the count of undrained V2 queue-delivered inputs per session.
- Incremented in `enqueueV2` (on successful admission)
- Decremented in `bridgeV2Prompted` (on V2 Prompted event — input was promoted/drained)
- Session removed from tracking only when count reaches zero (all pending inputs drained)

**`wakeStrandedV2Sessions`** (`proxy_v2.go`): called from `reconcileSessionState` on SSE reconnect. For each tracked session, POSTs a minimal `delivery:"queue"` prompt (`"\n"`) to trigger `execution.wake` → `runner.run` → drains all pending rows.

**Option B (proxy-side wake)** — fully in our control. Option A (upstream `POST /api/session/:sid/resume` endpoint) is the clean follow-up. Trade-off: the wake prompt creates one extra no-op turn per session.

---

## Key Decisions

1. **Tracking in `enqueueV2` only, not in `bridgeV2Admitted`.** The proxy's own action (enqueueV2 sends the prompt) is the authoritative tracking source. The V2 PromptAdmitted event is the SSE signal for frontend compatibility. Tracking at both sites causes double-counting (caught in review).

2. **Reference-counted tracking.** Multiple queue deliveries to the same session must not clear tracking when only one drains. The count must reach zero before removal.

3. **In-memory tracking, not Redis.** Per-replica tracking is sufficient for the SSE-reconnect case (same replica handles the workspace's event stream across reconnects). Multi-replica failover is an accepted edge case.

4. **`"\n"` as the wake prompt text.** Must be non-empty (F18: opencode rejects empty text). A newline is minimal pollution.
