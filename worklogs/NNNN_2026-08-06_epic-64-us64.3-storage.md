### Key implementations

**`CreateWorkflowRunWithFire`** (atomic fire-row + run-create): inserts `trigger_fires` + `workflow_runs` in a single Postgres transaction. If the run insert hits the single-in-flight unique violation, the whole tx rolls back — no orphan fire row claiming "fired" with no run. This is the v1 correctness pattern for webhook fire-row + run-create atomicity (design Edge Case 4). The caller then commits a separate `trigger_fires` row with `status=skipped` + `reason=already_running`.

**`ClaimQueuedRuns`**: `UPDATE ... SET status='running' WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED LIMIT N)`. Multiple controller replicas (or goroutines) can claim concurrently without contention. Returns the claimed rows with the new status already applied.

**`isUniqueViolation`**: detects SQLSTATE 23505 via the pgx error interface. Maps the single-in-flight partial index violation to `ErrConcurrentRun`.

## Key Decisions

1. **New `pkg/workflows/` package, not `pkg/secrets/`** — workflows is a bounded context separate from credentials. Putting it in `pkg/secrets/` would conflate "user-owned secrets" (the secrets subsystem's job) with "workflow orchestration state" (a different concern). The MCP store is in `pkg/secrets/` because MCP servers ARE user-owned secrets; workflows are not.

2. **pgxpool, not database/sql** — matches `PgSecretStore`. The Service-level `*sql.DB` is for legacy tables; new subsystems use pgxpool directly. Both flow through the same query tracer.

3. **No crypto in the store** — handlers encrypt webhook secrets before calling CreateWebhook; the receiver decrypts after calling GetWebhook. Mirrors the MCP store split exactly. The crypto envelope (KEK for org, session-DEK for user) is wired in US-64.5.

4. **`ON CONFLICT DO NOTHING` for dedup** — simpler than `INSERT ... RETURNING` + check. The `RowsAffected() == 0` case is the dedup hit. Returns `ErrDedupConflict` so the handler can return `200 "duplicate"` (idempotent re-delivery).

5. **`ClaimQueuedRuns` atomically marks runs running** — the `UPDATE ... WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED)` pattern means the claim and the status transition happen in one statement. No window where two replicas claim the same run.
