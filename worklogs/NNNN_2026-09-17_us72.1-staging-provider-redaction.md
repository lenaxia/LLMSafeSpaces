# Worklog: US-72.1 — StagingProvider envelope (KMS/HPKE) + dynamic staged-key redaction rules

## Objective

Land the D2 envelope: seal a provider key under a router-scoped key — KMS-wrapped local KEK (prod) or HPKE-seal to the router's public key (dev) — with a versioned, algorithm-discriminated wire format (`stg:v1:`), the plaintext `keyID` bound as GCM AAD, and the `llm-relay-kek` Secret contract (KMS-wrapped blob + key id, never plaintext KEK bytes). Plus the redaction integration: `pkg/redact` gains a minimal dynamic exact-value rule surface; the staging provider registers staged key material at seal/resolve and callers unregister on revocation. The router-side application of the combined pipeline to proxied traffic is US-72.2.

## Work Completed

### `pkg/secrets/staging_provider.go` (+ tests, + benchmarks)

- **Wire format** `stg:v1:<alg>:<keyID>:<base64(payload)>`, `alg` ∈ {`aes-256-gcm`, `hpke`}. The header (version + algorithm + plaintext keyID) is AEAD associated data in BOTH algorithms, so the discriminator is integrity-bound — an envelope cannot claim an algorithm or key it was not sealed under (`envelope_keyid_aad_bound` class, design §7).
- **KMS mode (prod):** `GenerateStagingKEK` / `BuildKEKSecretData` (one `kms.Encrypt`; Secret data = `key-id` + `wrapped-kek` only) / `ParseKEKSecretData` / `NewKMSStagingProvider` (one `kms.Decrypt` at construction — the only KMS call; the provider holds no KMS reference afterwards). `Seal`/`Resolve` are local AES-256-GCM via AAD-capable helpers local to this file.
- **HPKE mode (dev):** `HPKEStagingSealer` (public key only; implements `StagingSealer`, deliberately NOT `StagingResolver` — pinned by test) and `HPKEStagingResolver` (private key only; not a sealer). RFC 9180 base suite DHKEM(X25519, HKDF-SHA256) / HKDF-SHA256 / AES-128-GCM via `github.com/cloudflare/circl/hpke`.
- **Keypair machinery per design §4.2 (the envelope format the router speaks):** `HPKEKeyPairPayload` (`llm-relay-hpke-key`: privateKey, publicKey, generation — generation-tagged, self-contained), `HPKEPubPayload` (`llm-relay-hpke-pub`), `GenerateHPKEKeyPairPayload`, JSON marshal/parse with validation, `HPKEKeyID(generation)` (`hpke-g<N>`, derived by both sides so envelope keyIDs and Secret generations cannot drift), and `AssertHPKEKeyPair(payload, prevGeneration)` — the strictly self-contained integrity assert (derive pub from priv, compare against the co-located copy; generation monotonicity non-strict `≥` so informer re-list redelivery passes; never reads across Secrets).
- **Redaction seam:** `StagedKeyRedactor` interface, `RedactStagedKeys` adapter over `*redact.Redactor`, `StagedKeyRedactionID(envelope)` (`staged:<b64url(sha256(envelope)[:12])>` — both sides derive the same rule-group ID from the envelope alone), `StagedKeyMaterialRules` (raw / std-base64 / URL-base64 encodings of the material). Registration failures fail the seal/resolve loudly (fail-closed: a staged key that escaped the redaction engine is never delivered).

### `pkg/redact/redact.go` extension (+ tests)

- `DynamicRule{ID, Value, Replacement}` — exact-value (non-regex, byte-exact — arbitrary key material incl. non-UTF-8) rules grouped by ID; `(*Redactor).RegisterDynamic` (atomic group replace; validation failures leave no partial state), `(*Redactor).UnregisterDynamic`, and package-level `RegisterDynamic`/`UnregisterDynamic` on the shared cached redactor. RWMutex-guarded; concurrent Redact+Register covered under `-race`.
- **Dynamic rules run BEFORE the static pipeline** so a static pattern (e.g. `token=…`) cannot fragment a secret before the exact match removes it atomically.
- Existing 16 static rules untouched; behavior pinned byte-exact by a new golden corpus (`TestStaticPipelineGolden`, one row per rule, run with and without dynamic rules registered).
- New `pkg/redact/README.md` (the folder had none).

## Key Decisions

1. **Redaction and staging stay separate mechanisms** (owner's framing): `pkg/redact` is payload-hygiene only and knows nothing of staging/crypto; the staging provider is credential machinery. They interface at exactly the seal/resolve seam via the `StagedKeyRedactor` hook (nil = no registration), keeping the crypto API free of redaction bookkeeping.
2. **Envelope-derived rule-group ID** (`StagedKeyRedactionID`): controller (seal), router (resolve), and the revocation path (informer DeletedFunc sees the deleted envelope) all derive the same ID from the envelope alone — no shared state, no extra API parameters.
3. **Dynamic-before-static ordering** in the pipeline (fragmentation-proof removal), and **exact-value matching via `strings.ReplaceAll`** rather than quoted regexes — simpler, faster, and correct for non-UTF-8 material.
4. **Separate HPKE sealer/resolver types** rather than one dual-capability type: the compile/behavior pin ("controller holds no decrypt capability") is enforced by construction — `HPKEStagingSealer` has no private-key field and no `Resolve` method.
5. **KMS mode keeps one type** (`KMSStagingProvider`) with both Seal and Resolve: in prod both controller and router legitimately hold the KEK (each unwrapped once at boot), matching design §4.2.
6. **Envelope `alg` names** `aes-256-gcm` / `hpke` — the algorithm that sealed the payload, so prod/dev envelopes are interchangeable per deployment and cross-mode confusion is rejected before any AEAD work (loud `ErrStagingAlgorithmMismatch`), with the keyID check second and AEAD auth last.
7. **circl pinned at `v1.6.5`** (latest release): only the `hpke` + `kem` packages are imported; no other circl packages are reachable.
