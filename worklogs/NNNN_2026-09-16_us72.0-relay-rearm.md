## Design note (written BEFORE implementation — per #910 "Design note in worklog before implementation")

### D1 — The generalized loop is its own component; the injector is its first consumer

New file `cmd/workspace-agentd/rearm_loop.go`: `startRearmLoop(ctx, rearmLoopConfig)` — a single goroutine that
waits → gates → attempts → records outcome → re-arms. Gates are closures (`Applied`, `Busy`, `RestartDeferred`),
the work is an `Attempt(ctx) rearmAttemptResult` closure (`{outcome string, retryable, applied bool}`). No
injector-specific knowledge in the loop; no loop-specific knowledge in the attempt. US-72.4 (agentd relay-only
liveness/degrade codes) consumes the same loop with its own Attempt/gates — the story names this consumer, so the
seam is justified under Rule 12 (a funded second consumer, not speculation). It lives in `cmd/workspace-agentd`
(both consumers are agentd-internal; promoting to `pkg/` would require an exported API surface before the second
consumer's shape is known).

### D2 — Backoff schedule

Waits double from `MinDelay` (default 5m) capped at `MaxDelay` (default 30m): 5m → 10m → 20m → 30m → 30m …
(the #910-proposed schedule). Only a FAILED attempt advances the delay. A gate skip (busy / restart-deferred /
already-applied) neither advances nor resets it — a skip is not a failure. Terminal exits: attempt applied
(success → disarm), attempt non-retryable (personal key → permanent disarm), `Applied()` true at cycle entry
(`HasRelay()` re-check → disarm), ctx canceled (stop). Exactly one in-flight re-arm by construction: the loop is
one goroutine; `startRelayInjector` is called once per agentd process.

### D3 — Outcome taxonomy and metrics

The attempt returns the injector's EXISTING outcome strings (`fetch_failed`, `no_free_models`,
`unhealthy_timeout`, `config_write_failed`, `auth_write_failed`, `skipped_personal_key`, `success`,
`success_no_restart`), plus loop-level outcomes (`already_applied`, `busy`, `restart_deferred`, `canceled`).
Boot-window ticks stay in `llmsafespaces_relay_injector_total{outcome}` (unchanged label set, existing
dashboards/tests untouched); re-arm cycles tick the new generalized vec
`llmsafespaces_rearm_outcome_total{loop,outcome}` with `loop="relay_injector"` — the design's `relay_rearm_outcome`
metric realized as this loop's series of a generic vec (a relay-specific metric name would be wrong for US-72.4's
consumer). Exactly one tick per cycle with the cycle's final outcome.

### D4 — Kill-deferral interplay (#910's named constraint: attempts must not stack behind deferred kills)

A deferred restart implies sessions were busy at defer time — the re-arm `Busy` gate (the existing
`sessionStatusTracker` via `trackerHasBusyOrUnknown`) covers the steady state. The remaining window is the
≤`restartIdleCheckInterval` (5s) between the last busy→idle transition and the deferred goroutine's restart tick:
a re-arm attempt landing there would stack a second restart behind the pending one. Closed with a new
`deferredRestarts` atomic counter incremented/decremented around the deferred-restart goroutine in
`makeSessionAwareRestartDecision` (all call sites — credential apply, relay kill, XDG watcher — benefit), read by
the loop's `RestartDeferred` gate: skip the cycle (outcome `restart_deferred`) while any deferral is outstanding.
A successful re-arm's kill reuses `relayKillFunc` unchanged — i.e. the #1374 session-aware decision (unbounded
defer while progressing, interrupt-first force path) composes as-is. The re-arm loop disarms on success (the
writer's relay state is set before the kill), so the loop itself never re-fires behind its own kill.

### D5 — `HasRelay()` short-circuit and readyz truthfulness

Preserved twice: the boot-time Phase-D short-circuit (pre-boot applied → no injection at all) is untouched, and
the re-arm loop re-checks `HasRelay()` at every cycle entry (`already_applied` → disarm) — covering relay applied
by any other path mid-pod-life. readyz `RelayInjected` continues to evaluate `HasRelay()` live per request —
truthful per cycle by construction; pinned by test.

### D6 — Retryability classes

Retryable (re-arm): `fetch_failed`, `no_free_models`, `unhealthy_timeout`, `config_write_failed`,
`auth_write_failed`. Permanent (disarm): `skipped_personal_key` (personal Zen key = relay correctly bypassed).
Known residual (pre-existing, documented): Apply success + auth.json write failure leaves `HasRelay()` true with a
missing auth entry; the next cycle disarms via `already_applied` — same terminal state as the one-shot injector.

### D7 — Context and lifecycle

The loop lives under the injector's existing `rootCtx` (SIGTERM-scoped). Cancel while waiting → one `canceled`
tick + exit; cancel during an attempt → the attempt's inner fetch loops return `canceled` → tick + exit. Each
re-arm cycle runs one full bounded fetch attempt (same `FetchDeadline` as boot, default 30s).

### D8 — statusz `relayFreeModelsState` (#901 G8) semantics under re-arm

State stays 2 (degraded) while re-arm cycles fail; the first successful cycle flips it to 1. The stale-window
wording ("degraded until the next agent restart") is deleted wherever it appears — recovery is now bounded by the
backoff, and README-LLM.md's relay-config section is updated where this change makes it stale (Rule 5).
