## Objective

## Work Completed

### Router binary (`cmd/relay-router`, new files; fleet router untouched)

- **Mode**: `ROUTER_MODE=byo` runs `runBYO` — same binary, separate Deployment in `llm-relay` (decision below).
- **Tokens** (`byo_token.go`): `lrt_<b64url(payload)>_<HMAC-SHA256>` per §4.4; payload `{workspaceID, providerSlug, baseURL, modelAllowlist, iat, exp, keyID}`; 30s clock-skew tolerance both directions (pinned).
- **Keypair machinery** (`byo_keys.go`): create-or-adopt first boot (API-server create = serializer, pub-Secret heal, boot-time corruption triggers the same DR as watch-time), watch loads re-running `AssertHPKEKeyPair` every delivery (non-strict ≥ — redelivery passes), dual-key resolve window with time-bounded prior-key retention (default 10m, lazily swept), controller-driven `Rotate` (private-then-pub ordering, generation-preconditioned so a concurrent winner aborts the loser before pub), and DR self-rotate (precondition = the observed-failing generation; keyIDs kept strictly monotonic — `max(failing+1, highwater+1)` — so dead-key envelopes fail as the clean unknown-keyID `credential_stale`, never a noisy AEAD error).
- **Informer cache** (`byo_cache.go`): ciphertext-only envelope cache keyed by `(workspace, provider)` labels; revocation = Secret deletion → eviction → 401 `credential_stale` (K5). `resolveDispatcher` routes by envelope algorithm: `aes-256-gcm` → the KMS-mode resolver, `hpke` → generation-keyed resolvers (`pkg/secrets.InspectStagingEnvelope`, new in this PR).
- **Sanitization** (`byo_sanitize.go`, §4.7): client Authorization replaced by the resolved key (never forwarded); identity/hop headers stripped (incl. `X-Relay-*`, `X-Llmsafespaces-*` wildcards, workspace/forwarding/cookie); method/path allowlist (chat-completions-class + `/models`); request cap 10 MiB / response cap 50 MiB; model-allowlist enforcement (re-reading the batch-side check, defense in depth).
- **Redaction seam (§4.9, consuming US-72.1)**: request bodies are redacted with the **dynamic staged-key exact-value rules** (full buffer); responses stream through a carry-window redactor (`byo_cache.go`) so a key split across chunks is removed whole. `Resolve` registers material with the shared `*redact.Redactor` (the US-72.1 seam), so the rules are live before the first byte forwards. Diagnostics/log lines carry sanitized metadata only (K7) — `sanitizeMeta` strips control characters (log-injection guard).
- **Quotas** (`byo_quota.go`): per-workspace sliding-window request/byte budgets with 429 + `quota_exceeded`; metrics `llm_relay_byo_*`; Helm alert rules (reject spike, upstream errors).
- **Internal API**: `POST /internal/v1/tokens` (mint; TTL-bounded) and `POST /internal/v1/keys/rotate` — controller-authenticated by the Secret-held mint key (`llm-relay-mint-key`, lazily read + cached so controller/router boot ordering never wedges; constant-time compare).
- **Drain**: SIGTERM → `Shutdown` bounded by `BYO_DRAIN_GRACE` (600s default; `terminationGracePeriodSeconds` 630 in Helm) — a cap, not a delay (#1078).

### Helm (`relayOnlyKeyDelivery.enabled`, default **false** until US-72.5)

`llm-relay` namespace, Deployment ×2 + PDB `maxUnavailable: 1`, Service, NetworkPolicy (workspace-namespace ingress carve-out), RBAC per §4.3 — router SA: `get/list/watch` Secrets + name-scoped `create/update` on **exactly** the two keypair Secrets; controller SA: `create/update/delete` the other llm-relay Secrets + `get` on `llm-relay-hpke-pub` only (never the private-key Secret). ## Key Decisions

1. **Deployment shape: separate Deployment** (`llm-relay-router` in `llm-relay`, same binary via `ROUTER_MODE=byo`) — the story's leaning, confirmed: blast radius (BYO traffic vs free-tier fleet), quota models, and RBAC namespaces differ; a second listener would couple health, drain, and metrics lifecycles of two unrelated services.
2. **Bodies get dynamic-only redaction; diagnostics get the full static+dynamic pipeline.** The §4.9 named threat — "a resolved key can never be echoed back through the relay" — is fully covered by the exact-value staged-key rules (zero false positives). The static heuristics (40+ char base64, `token=`…) would corrupt legitimate structured/vision payloads (base64 image parts are a live wire format, issue #1307) — and §3 already accepts the general exfil-through-relay content channel as quota-bounded. `pkg/redact` gains `DynamicRules()`/`RedactDynamicOnly()` for this surface. Flagged for the owner in the PR body as a marked refinement of §4.9's wording.
3. **DR keeps keyIDs strictly monotonic** (`max(failing+1, highwater+1)`): a DR minting a reused keyID would make dead-key envelopes fail as AEAD auth errors instead of the clean unknown-keyID `credential_stale` discrimination the design's re-seal machinery reads.
4. **Rotation precondition = the generation the caller observed** (design's exact wording): operator rotation compares against the local high-water mark; DR compares against the observed-failing generation; unparseable DR falls back to resourceVersion-only serialization (single lineage).
5. **KMS-mode router wiring deferred to US-72.5's prod bring-up**: the dispatcher seam exists and is pinned (`aes-256-gcm` envelopes route to `resolveDispatcher.kms`); constructing the cloud KMS client in the router Deployment is deployment plumbing (credentials/ARNs per cloud) that belongs with the canary story. HPKE mode is fully end-to-end here. K2 (zero KMS at steady state) is pinned in `pkg/secrets` benchmarks.
6. **Mint key is Secret-held and lazily cached** (60s TTL, last-known-good through outages) rather than boot-required — controller/router boot ordering never wedges, rotation converges without restart.
