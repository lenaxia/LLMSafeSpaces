# Worklog 1231 — #1964: Task Board UI — archived projects collapse into a bottom drawer

- **Date**: 2026-10-26
- **Lane**: lane-1964 (orchestrator: novel-nutmeg-verifies)
- **Issue**: #1964
- **Type**: Frontend feature (presentation hierarchy), no API change

## Context

Owner directive: archived projects remained visible on the Task Board like
active ones (inline swimlanes with an "archived" badge). They must be HIDDEN
from the main board and live in a collapsed **Archived section at the end of
the board**; each archived project inside is itself a collapsed drawer showing
ONLY its name until clicked. History stays reachable — purely presentation
(#1755 semantics untouched).

## Validation first (what the code does today)

- `frontend/src/pages/BoardPage.tsx` is the whole board. Projects render as
  swimlanes (`visibleProjects.map`, swimlane map was inline at ~line 787);
  archived projects were NOT hidden — they arrived in the same
  `GET /me/projects` list (`status:"archived"` rides the row;
  `pkg/board/reads.go` `ListProjects` does not filter) and rendered inline
  with a muted badge + "Unarchive project" kebab. The focus dropdown listed
  them with a " — archived" suffix.
- No backend work needed: the listing already returns archived rows; the
  sessions surface (`Sidebar.tsx`) already established the exact
  collapsed-archived-group pattern (#1627, `ArchivedGroup`, lines 1153-1238)
  — collapsed by default, deliberate friction, chevron + Archive icon +
  count, `aria-expanded`/`aria-label`.

## Decisions / ruling anchors

- **No `include_archived` API flag**: the read already returns archived rows
  (checked `api/internal/handlers/board.go` `ListProjects` →
  `pkg/board/reads.go`); the split is client-side, mirroring how the Sidebar
  splits sessions after an opted-in fetch. Backend untouched.
- **Deliberate friction** (#1627 ruling 3, applied to projects): both levels
  collapsed by default; nothing auto-expands — not even archiving a project
  mid-session.
- **History reachable**: the drawer renders the SAME swimlane
  (`renderSwimlane`), not a summary — task bands, stage columns, task
  details, and Unarchive all work inside; the engine's archived guards
  remain the arbiter for any write (task_start/pause refuse, #1755).
- **Scope-creep guard**: COMPLETED-epic collapsing inside active projects
  noted as follow-up in the CHANGELOG; NOT implemented (owner did not ask).

## r1 — CHANGES_REQUESTED review (2026-10-26T19:53:07Z, head f7b2d503) — addressed

Reviewer findings (review id 5658107779), each addressed in this revision:

1. **Drawer lane rendered an empty scaffold under an active project focus**
   (contradicted issue criterion 4 "history stays reachable"). The tasks
   read short-circuited to the focused lane (`listProjectTasks(focus)`)
   while the drawer renders regardless of focus — its lanes had band
   headers (the epics fan-out covers all projects) but zero rows. Fix:
   the tasks read is ALWAYS the full fan-out (`queryKey: ["board",
   "tasks"]`, no focus arm) — matching the epics fan-out beside it and
   the PR's own stated design ("the tasks/epics fan-outs still fetch
   every lane: drawer content needs them"). Focus stays a pure VIEW
   filter (`visibleProjects`); a cached full board also makes focus
   switches instant (no refetch flash). Pinned: "expanding a drawer
   lane under an ACTIVE project focus still renders its history".
2. **Cross-context archive of the focused lane stranded the board.** The
   in-session archive path resets focus (`handleProjectLifecycle`), but
   another tab/session's archive rides the `board.event` `["board"]`
   invalidation: the refetch drops the lane from `activeProjects` while
   `focusProject` still names it — `visibleProjects` = [] with active
   lanes alive, the select matching no option, no hint, no recovery.
   Fix: a focus guard effect resets scope to All the moment the focus
   id stops naming an active lane (covers cross-context archive, any
   future lane disappearance, and belt-covers the in-session path).
   Pinned: "a focused lane archived cross-context (refetch lands it
   archived) resets focus — never a stranded board" — drives the real
   `invalidateQueries(["board"])` through the harness's exposed
   QueryClient (the exact board.event branch trigger).
3. **(Minor) Stale `tagFilter` after archiving the tag's lane.** The
   chip derives from the ACTIVE surface (`allTags` ← `surfaceTasks`), so
   archiving the tag's only lane vanished the chip while
   `filteredTasks` kept applying it — rows silently hidden with no
   visible chip to clear. Fix: a filter guard effect drops `tagFilter`
   the moment its tag leaves the toolbar. Pinned: "archiving the
   tag-filtered lane drops the filter with its chip".

Collateral updates: `BoardPage.scope.test.tsx`'s "focused fetch is the
single-project REST call" assertion rewritten to the full-fan-out
contract (every lane's call fired; focus is a view filter);
`boardTestUtils.renderBoard()` now exposes its QueryClient (return type
extended — all existing call sites ignore the return).

## r2 — CHANGES_REQUESTED review (2026-10-26T22:26:56Z, head 1f1f826e6) — addressed

Reviewer confirmed all three r1 fixes genuinely fixed (each pin
mutation-verified red in a scratch worktree by the reviewer). One new
validated finding survived the second pass:

1. **Drawer expansion state went stale across archive lifecycle
   transitions.** `archivedDrawerExpanded` / `expandedArchivedProjects`
   were click-owned but nothing reconciled them when their object left:
   - Project level: expand archived P → unarchive → re-archive → P's
     drawer row re-entered PRE-EXPANDED (full swimlane, no click) —
     violating criterion 3's "name only until clicked" on every entry.
   - Outer level: open the drawer → unarchive the last archived lane
     (section unmounts, state persists) → a later archive re-rendered
     the section ALREADY EXPANDED — violating the founding "nothing
     auto-expands, not even an archive landing mid-session" posture.
   Fix (the same reactive stale-view-state treatment as r1's guards):
   an id-prune effect drops a project's expanded row the moment it
   leaves `archivedProjectIds` (returns the same Set reference when
   nothing changed — no re-render loop), and an empty-drawer effect
   collapses the outer section so any later archive lands collapsed.
   Cross-context covered by construction (the effects key on the read
   model, not on any session's actions).

Pins (both red-verified against the disabled guards — exactly 2 tests
fail under mutation, nothing else):
- "a re-archived project renders its drawer row COLLAPSED again
  (name-only, no click)" — unarchive→re-archive round-trip.
- "an archive landing into a previously-emptied drawer leaves the
  section collapsed (nothing auto-expands)" — cross-context archive via
  the real `invalidateQueries(["board"])` drive.
